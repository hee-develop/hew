# 티켓 분해안(`plan`) 형식 안내

`hew submit plan` 으로 내는 JSON 파일의 형식이다. 최상위는 `items` 가 아니라 아래 묶음을 바로 가진 객체다(공통 틀은 코어가 씌운다). 정확한 예시는 이 폴더의 파일이다.

- 통과하는 분해안 예시: `refs/plan.example.json`
- 그 예시가 가리키는 분석 문서: `refs/analysis.example.json` (요구와 변경 항목을 거기서 읽는다)
- 그 예시가 따르는 사람의 답과 결정: `refs/answers.example.json` (차이 D-1 이 `hold` 라서 요구-2 가 범위 밖이다)
- 분해 규칙: `rules/plan.yaml` (SP 범위, 제목 형식, 본문에 쓰면 안 되는 것, PR 하나의 티켓 수 상한)

예시는 실제 일감의 내용이 아니라 형식을 보이는 합성 자료다. 칸의 모양과 id 쓰는 법만 따르고 내용은 베끼지 않는다. 분해안은 정본 분석 문서(`doc/analysis.json`)와 사람의 답(`doc/answers.json`)이 있어야 검사받는다.

## 쓰는 규칙

- 아래 표에 없는 칸을 만들지 않는다. 스키마에 없는 키는 코어가 버리고 경고(`unknown_field_dropped`)를 낸다.
- 표의 "필수" 는 스키마가 요구하는 칸이다. "검사" 는 칸 자체는 비워도 되지만 결정적 검사가 채우라고 요구하는 경우다. "선택" 은 비워도 된다. 목록 칸은 비우면 `[]` 다.
- id 형식: 티켓 `Tn`, PR 묶음 `PR-n`. n 은 1 부터 시작하는 숫자다. 요구는 분석 문서의 id(`요구-n`)를 그대로 쓴다. 같은 종류의 id 를 두 번 쓰지 않는다.
- 티켓은 사람이 읽는 문서다. 코드 경로, 파일 이름, 확장자, 줄 번호, 함수 호출 모양(`foo()`)은 본문에 쓰지 않는다. 화면 이름과 바뀌는 문구를 정확히 적는다.
- 사람이 게이트에서 `hold`(보류)나 `drop`(구현 안 함)으로 정한 차이에 걸린 요구는 요구 전체를 범위 밖으로 본다. 범위 밖 요구는 티켓에 넣지 않고 `excluded` 에 이유와 함께 적는다.

## 최상위

| 칸 | 형식 | 필수 | 뜻 |
|---|---|---|---|
| `epic_name` | 문자열 | 필수 | 일감명. 모든 티켓 제목의 `{일감명}` 과 같아야 한다 |
| `parent` | 문자열 | 선택 | 티켓을 달 스토리 키(예: `APP-3008`) |
| `tickets` | 객체 배열 | 필수 | 티켓 |
| `prs` | 객체 배열 | 필수 | PR 묶음 |
| `feature_flag` | 객체 | 선택 | 피처플래그 사용 여부. 비우면 쓰지 않는 것으로 본다 |
| `excluded` | 객체 배열 | 선택 | 보류·구현 안 함으로 뺀 것과 이유 |

## tickets[] — 티켓

| 칸 | 형식 | 필수 | 뜻 |
|---|---|---|---|
| `id` | `Tn` | 필수 | 티켓 id |
| `title` | 문자열 | 필수 | `[MO] {일감명} / {작업 요약}`. 스쿼드 접두어는 붙이지 않는다 |
| `body` | 객체 | 필수 | 본문(아래 표) |
| `requirement_ids` | 요구 id 배열 | 검사 | 덮는 요구. 비면 플래그 제거 티켓(`feature_flag.removal_ticket`)만 허용된다 |
| `changes` | 객체 배열 | 선택 | 요구의 일부 변경만 맡을 때 `{ requirement_id, index }`. `index` 는 그 요구 `changes` 배열의 0부터 위치다 |
| `sp` | 숫자 | 필수 | Story Points. 1SP 는 1시간이다. 기본 범위는 2~4SP |
| `depends_on` | 티켓 id 배열 | 선택 | 먼저 끝나야 하는 티켓 |
| `pr` | `PR-n` | 필수 | 속한 PR 묶음 |

- 티켓이 `changes` 없이 `requirement_ids` 에 요구를 적으면 그 요구의 변경 항목 전부를 맡은 것이다. 요구 하나를 여러 티켓으로 나눌 때는 티켓마다 `changes` 로 맡은 변경 항목을 적고, 합쳐서 그 요구의 변경 항목이 모두 있어야 한다. `changes` 의 `requirement_id` 는 그 티켓의 `requirement_ids` 에도 있어야 한다.
- 범위 안의 모든 요구의 모든 변경 항목이 어느 티켓에든 들어가야 한다.

`body`

| 칸 | 형식 | 필수 | 뜻 |
|---|---|---|---|
| `background` | 문자열 | 검사 | 배경. 왜 필요한가, 어디서 온 요청인가 |
| `work` | 문자열 배열 | 검사 | 작업 내용. 글머리표 항목 하나 이상. 무엇이 바뀌는가 |
| `checks` | 문자열 배열 | 선택 | 확인 사항 |
| `depends_note` | 문자열 | 선택 | 선행 의존의 설명 |
| `refs` | 문자열 배열 | 선택 | 참고(상위 스토리, PRD, 시안 링크 이름) |
| `tracker_events` | 객체 배열 | 선택 | 트래커 작업이면 `{ name, when, properties[] }` 의 이벤트 표 |

- 본문 순서는 배경, 작업 내용, 확인 사항·선행 의존, 참고다. 한 줄로 끝내지 않는다.
- 화면을 그리는 일과 동작을 붙이는 일은 리뷰할 때 대조하는 것이 다르다. 한 티켓에 넣더라도 작업 내용 항목을 나눠 적는다.

## prs[] — PR 묶음

| 칸 | 형식 | 필수 | 뜻 |
|---|---|---|---|
| `id` | `PR-n` | 필수 | PR 묶음 id |
| `title` | 문자열 | 필수 | 제목 |
| `ticket_ids` | 티켓 id 배열 | 검사 | 묶인 티켓. 티켓의 `pr` 과 서로 맞아야 한다. 규칙 상한(6개)을 넘으면 경고 |
| `base` | `develop` 또는 `PR-n` | 필수 | 어느 브랜치 위에 쌓는가. `PR-n` 이면 그 PR 의 `order` 가 더 작아야 한다 |
| `order` | 숫자 | 필수 | 병합 순서. 작을수록 먼저다 |

- 티켓 A 가 B 에 의존하면 A 의 PR 의 `order` 는 B 의 PR 의 `order` 이상이어야 한다(같은 PR 이면 통과).
- 요구 X 가 요구 Y 에 의존하면, X 를 맡은 티켓의 PR `order` 는 Y 를 맡은 티켓들의 PR `order` 최댓값 이상이어야 한다.
- 티켓과 PR 의 의존·base 사슬에 순환이 있으면 안 된다.

## feature_flag — 피처플래그

| 칸 | 형식 | 필수 | 뜻 |
|---|---|---|---|
| `used` | 불리언 | 필수 | 피처플래그를 쓰는가 |
| `name` | 문자열 | 선택 | 플래그 이름 |
| `removal_ticket` | 티켓 id | 검사 | `used` 가 참이면 필수. 플래그를 걷어내는 티켓이고, 그 티켓의 PR 이 `order` 최대여야 한다 |

- 플래그를 쓰는 일감은 에픽 브랜치를 만들지 않는다. 첫 PR 의 `base` 는 `develop` 이고, 의존이 있으면 앞 PR 위에 쌓는다.

## excluded[] — 뺀 것

| 칸 | 형식 | 필수 | 뜻 |
|---|---|---|---|
| `kind` | `delta`·`requirement`·`change` | 필수 | 무엇을 뺐는가 |
| `ref` | 문자열 | 필수 | `delta` 면 차이 id(`D-n`), `requirement` 면 요구 id, `change` 면 `요구-n#<index>` |
| `reason` | 문자열 | 필수 | 왜 뺐는가(보류, 구현 안 함) |

- 범위 밖 요구가 `excluded` 에 없으면 경고(`excluded_missing`)가 난다. 요구를 범위 밖으로 만든 차이를 `delta` 로 적거나, 요구 자체를 `requirement` 로 적는다.

## 사람의 수정 요청

게이트에서 사람이 분해안에 수정 요청을 냈으면 패킷에 표로 실린다. 요청대로 고치되 요구는 바꾸지 않는다. 요청이 요구를 바꿔야만 가능하면 분해안은 요구에 맞게 두고 보고에 적는다. 코어는 요청이 들어와 있다는 정보 지적(`plan_change_unaddressed`)만 내고 반영 여부는 사람이 승인 단계에서 확인한다.

## 자주 거부되는 이유

| 코드 | 이유 | 고치는 법 |
|---|---|---|
| `requirement_unmapped` | 범위 안 요구의 변경 항목을 맡은 티켓이 없다 | 티켓의 `requirement_ids`(필요하면 `changes`)에 넣는다 |
| `ticket_orphan` | 맡은 요구가 없는 티켓이다 | 요구를 적거나, 플래그 제거 티켓이면 `feature_flag.removal_ticket` 으로 지정한다 |
| `hold_included` | 보류·구현 안 함으로 정한 요구를 티켓이 맡았다 | 그 요구를 티켓에서 빼고 `excluded` 에 적는다 |
| `title_format` | 제목이 `[MO] {일감명} / {작업 요약}` 이 아니거나 일감명이 `epic_name` 과 다르다 | 모든 제목을 같은 일감명으로 맞춘다 |
| `body_sections` | 배경이나 작업 내용이 비었다 | 둘 다 쓴다 |
| `body_code_detail` | 본문에 파일 경로·확장자·줄 번호·함수 호출 모양이 있다 | 화면 이름과 문구로 바꿔 쓴다 |
| `dependency_cycle` | 티켓 의존이나 PR base 에 순환이 있다 | 순환을 끊는다 |
| `plan_ref_missing` | 없는 요구·티켓·PR 을 가리킨다 | id 를 확인한다 |
| `pr_base_order` | 의존하는 티켓의 PR 이 먼저 병합되거나 base 의 순서가 더 크다 | `order` 와 `base` 를 맞춘다 |
| `ticket_without_pr`, `pr_ticket_mismatch` | 티켓의 `pr` 과 PR 의 `ticket_ids` 가 맞지 않는다 | 양쪽을 맞춘다 |
| `flag_removal_last` | 플래그를 쓰는데 제거 티켓이 없거나 마지막이 아니다 | 제거 티켓을 마지막 PR 에 둔다 |
| `requirement_dependency_broken` | 요구의 의존 순서가 PR 순서에서 뒤집혔다 | 먼저여야 하는 요구의 티켓을 앞 PR 에 둔다 |
| `id_format`, `id_duplicate` | id 형식이 틀리거나 겹친다 | `Tn`, `PR-n` 으로 다시 센다 |

경고(`sp_range`, `pr_too_large`, `excluded_missing`)는 거부하지 않지만 게이트의 "확인 필요" 에 올라간다.
