## 0. 범위

### 0.1 다루는 것

설계 문서 §12 의 "1번 단계"다. 입력(PRD URL 또는 Jira 티켓 URL)에서 사람의 승인까지, 그리고 이 구간의 완료 기준을 재는 평가 장치다.

```
입력 → [0] 수집 → [1] 분석(테크니컬 매니저) → [1] QA 설계 → [1-1] 매니저 사수
     → 게이트(답변) → 답 반영 → [2] 티켓 메이커 → [2-1] 티켓 사수 → 게이트(승인) → 잠금
```

- 수집, 원문 단위 열거
- 요구사항 분석 문서, QA 시나리오, 티켓 분해안의 스키마와 결정적 검사
- 매니저 사수, 티켓 사수의 작업 단위와 지적 형식
- 게이트 페이지와 답·결정·승인의 저장 형식
- 코어 명령 계약, 상태 기계, 에이전트 실행기
- 리플레이, 결함 주입, 채점, 완료 기준
- 실수 기록 형식

### 0.2 다루지 않는 것

Jira 쓰기 단계, 빌더, 빌더 사수, 코드 리뷰, QA 실행, PR 작성, 승인 뒤 요구 변경 처리, 종료 보고서. 다만 이 단계들이 읽을 산출물의 형식은 여기서 정한다.

### 0.3 이 명세에서 새로 둔 가정

| # | 가정 | 이유 | 절 |

## 1. 실행 모델

### 1.1 구성 요소

| 요소 | 위치 | 하는 일 |
|---|---|---|
| 코어 | `src/`, 명령 `bin/hew` | 상태, 스키마 검증, 결정적 검사, 패킷 생성, 에이전트 실행, 게이트 페이지 생성, 채점 |
| 역할 정의 | `agents/<역할>.md` | 역할별 지시문. 버전은 git SHA 로 기록한다 |
| 게이트 생성기 | `gate/` | 정본 JSON 에서 Artifact 페이지(HTML)와 올릴 이미지 목록을 만든다 |
| 세션 스킬 | `skills/hew-gate/` | 대화형 세션에서 게이트 페이지를 게시하고 답을 읽어 코어에 넘긴다. 다른 판단은 하지 않는다 |
| 규칙 파일 | `rules/` | 티켓 분해·PR 묶음 규칙, 경험 점검표, 개인 습관 설정(팀으로 넓힐 때 갈아 끼울 지점) |

- 대상 저장소(mobile-app)의 경로와 base 브랜치는 실행 설정으로 받는다.

### 1.2 실행 폴더

실행 하나에 폴더 하나다. 기본 위치는 `~/hew-runs/<run_id>/` 이고 `run_id` 는 `<날짜>-<일감 키 또는 PRD id>-<일련번호>` 다. [가정]

```
run.json              상태(단계, 모드, 현재 revision, 입력)
events.jsonl          일어난 일의 기록(덧붙이기만 한다)
costs.jsonl           에이전트 실행별 비용·시간·모델
mistakes.jsonl        실수 기록(§12)
sources/              원천 스냅샷(§3)
  manifest.json
  prd/  figma/  code/  openapi/  related/
  units.json          원문 단위
packets/              에이전트에 준 입력(실행별로 보존)
work/<실행 id>/       에이전트의 작업 폴더(제출 전 초안)
doc/                  검증을 통과한 정본
  analysis.json  scenarios.json  plan.json
  findings/<단계>-<회차>.json
  answers.json        게이트에서 들여온 답·결정
gate/                 page.html  assets/  url.txt  db-export.json
approval.json         승인 기록(잠근 revision)
```

- 정본(`doc/`)은 코어만 쓴다. 에이전트는 `work/` 에 쓰고 `hew submit` 으로 낸다.
- 평가 모드의 채점표(gold)는 실행 폴더 밖에 둔다(§11.2).

### 1.3 상태 기계

| 상태 | 들어오는 조건 | 다음 |
|---|---|---|
| `init` | `hew init` | 수집 |
| `collected` | 필수 원천이 모두 등록되고 원문 단위가 열거됨 | 분석 |
| `analyzed` | `analysis` 제출이 결정적 검사를 통과 | QA 설계 |
| `qa_designed` | `scenarios` 제출이 검사를 통과 | 매니저 사수 |
| `checked` | 사수의 차단 지적이 0건이거나, 반송 상한(2회)에 닿아 남은 지적을 게이트 질문으로 바꿈 | 게이트 게시 |
| `gate_answering` | 게이트 페이지가 게시됨 | 사람의 답 |
| `answers_complete` | 모든 질문에 답, 모든 차이에 결정, 모든 가정에 확인이 들어옴 | 답 반영 |
| `answers_applied` | 답을 반영한 `analysis`·`scenarios` 재제출이 검사와 사수 재확인(바뀐 항목만)을 통과 | 티켓 메이커 |
| `planned` | `plan` 제출이 검사를 통과 | 티켓 사수 |
| `plan_checked` | 티켓 사수의 차단 지적 0건 또는 상한 도달 | 게이트 재게시 |
| `gate_plan_review` | 분해안이 실린 게이트 페이지가 게시됨 | 사람의 승인 또는 수정 요청 |
| `approved` | 페이지가 보낸 revision 이 코어의 현재 revision 과 같음 | (2번 단계 이후) |

- 수정 요청이 오면 `planned` 앞으로 돌아가 티켓 메이커를 다시 돌린다. 요구는 바뀌지 않는다.
- `gate_answering` 중에 답이 요구를 바꿔 새 질문이 생기면 다시 `gate_answering` 이다. 이미 답한 질문 중 근거가 바뀐 것은 "다시 답 필요"로 표시한다(heka `hew-superseded-79fa26`).
- 상태는 제출·검사·들여오기 명령의 결과로만 바뀐다. 에이전트의 완료 선언은 상태를 바꾸지 않는다.
- 어느 상태에서든 실행이 죽으면 `hew run` 을 다시 부르면 같은 상태에서 이어 간다.

### 1.4 에이전트 실행기

코어의 `hew run` 이 상태를 보고 다음 역할을 새 세션으로 띄운다.

```
claude -p "<패킷 경로를 읽고 수행하라는 고정 문장>" \
  --agent hew:<역할> --plugin-dir <hew> \
  --model <모델> --effort <effort> \
  --permission-mode dontAsk --allowedTools <역할별 목록> \
  --setting-sources project,local --strict-mcp-config --mcp-config '{"mcpServers":{}}' \
  --settings <실행용 설정(훅)> --output-format json < /dev/null
```

- 수집 역할만 예외다. 연결된 커넥터(Atlassian, Figma)를 써야 하므로 `--setting-sources`·`--strict-mcp-config` 를 붙이지 않는다.
- 그 밖의 역할은 사용자 설정의 훅·플러그인·MCP 없이 뜬다. 2026-11-14 실측에서 이렇게 띄운 세션은 사용자 훅이 0번 돌고 MCP 서버가 0개였으며 로그인은 그대로 됐다. [사실]
- 표준 입력을 닫지 않으면 세션이 입력을 3초 기다린다. [사실]

- `--bare` 는 쓰지 않는다. 구독 로그인을 읽지 않기 때문이다. [사실: headless 문서 "bare mode doesn't use your subscription login"]
- 결과 JSON 에서 `total_cost_usd`, `num_turns`, `session_id`, 오류 여부를 `costs.jsonl` 에 남긴다.
- 세션이 끝나면 코어가 상태를 다시 읽는다. 기대한 제출이 없으면 그 실행은 실패다. 같은 역할을 최대 2회 더 띄우고, 그래도 없으면 실행을 멈추고 사람에게 알린다(승인 전이므로 사람이 세션에 있다). [가정]
- 사용량 한도로 실패하면 리셋 시각까지 기다렸다 같은 역할을 다시 띄운다. 한도 실패를 어떻게 구분하는지는 [미결: 실측].

역할별 설정 [모델·effort 는 가정, 평가로 조정]

| 단계 | 역할 | 모델·effort | 허용 도구 | 읽는 것 | 내는 것 |
|---|---|---|---|---|---|
| 0 | `collector` | Sonnet 5.5 `medium` | Atlassian·Figma 읽기 MCP, ToolSearch, Bash(`hew source *`, `curl`), Read | 수집 계획 | 원천 등록 |
| 1 | `technical-manager` | Opus 5.5 `high` (Fable 5.2 `medium` 과 비교, 설계 §4.5) | Read, Bash(`hew *`, 검색·보기 명령, 읽기 전용 `git`, `sips`) | 원천 스냅샷, 대상 저장소 | `analysis` |
| 1 | `qa-designer` | 위와 같다 | Read, Bash(`hew *`, 검색·보기 명령) | `analysis`, OpenAPI, 대상 저장소 | `scenarios` |
| 1-1 | `manager-sasu` | Haiku 5.5 | Read, Bash(`hew submit findings`) | 작업 묶음 파일 하나 | `findings` |
| 2 | `ticket-maker` | Sonnet 5.5 `medium` | Read, Bash(`hew *`, 검색·보기 명령) | 답이 반영된 `analysis`, 규칙 파일 | `plan` |
| 2-1 | `ticket-sasu` | Haiku 5.5 | Read, Bash(`hew submit findings`) | 작업 묶음 파일 하나 | `findings` |

- 분석 에이전트는 Atlassian·Slack 도구를 받지 않는다. PRD 와 관련 문서는 수집 단계가 스냅샷으로 넣어 둔 것만 읽는다(§3).
- 역할 세션에는 heka 도구를 주지 않는다. 따를 규칙의 본문은 코어가 패킷에 실어 준다(§9). 모드에 따라 달라지는 것은 코어가 읽는 시점뿐이다. [가정]
- 이 버전(2.1.323)의 무인 세션에는 Grep·Glob 도구가 따로 없다. 검색은 Bash 의 허용 명령(`rg`, `grep`, `ls`, `find`, `cat`, `head`, `wc`, `jq`)으로 한다. [사실]
- Figma 는 수집 단계가 화면 목록과 스크린샷을 넣어 두되, 분석 중 더 봐야 할 노드가 있으면 테크니컬 매니저가 `hew source request` 로 요청하고 수집 단계가 한 번 더 돈다. [가정] 분석 에이전트에 Figma 도구를 직접 주는 안은 호출 한도와 스냅샷 밖 인용 문제 때문에 택하지 않았다.
- 읽기·쓰기 범위는 실행용 설정의 훅(PreToolUse)이 지킨다. 읽기는 실행 폴더와 대상 저장소(사본) 안으로, 쓰기는 `work/<실행 id>/` 안으로 제한한다. Bash 는 허용 명령만 받고, 명령에 든 경로가 범위 밖이면 거부한다. 2026-11-14 실측에서 Read 의 범위 밖 경로와 `..` 경로가 거부됐다. [사실]
- Fable 5.2 를 `medium` 으로 쓸 때는 역할 정의에 "끝까지 진행" 문구를 넣는다(설계 §4.5).
- 사수 세션의 고정 비용은 작다. 도구를 줄이고 사용자 설정 없이 띄운 Haiku 5.5 세션 한 번이 약 $0.001 이었다(도구 199개가 실린 기본 세션은 $0.006~0.010). [사실, 2026-11-14] 그래도 작업 단위는 묶음으로 준다(§6.3).

### 1.5 제출과 검증

- 에이전트는 초안을 `work/` 에 쓰고 `hew submit <종류> --file <경로>` 를 부른다.
- 코어는 스키마, 참조 무결성, 결정적 검사를 돌린다. 거부(종료 3)면 정본은 그대로이고 오류 목록을 돌려준다. 에이전트는 같은 세션에서 고쳐 다시 낸다.
- 통과하면 코어가 공통 틀(§2.1)을 씌워 `doc/` 에 쓰고 이벤트를 남긴다.
- 게이트에 한 번이라도 게시된 뒤의 재제출에서는 사람이 답했거나 결정한 항목을 에이전트가 지우지 못한다. 지우려면 `--withdraw <id>` 로 명시하고, 사람 입력이 있는 항목은 거부한다(heka `hew-submit-withdraw-2026-10-29`).
- 재제출에서 같은 항목은 같은 id 를 유지한다.

### 1.6 실행 모드

| 모드 | 원천 | 외부 쓰기 | heka | 게이트 |
|---|---|---|---|---|
| `live` | 현재 버전 | 승인 뒤 쓰기 단계에서만 | 현재 | 사람이 답한다 |
| `replay` | 사례 파일이 정한 과거 버전 | 없다 | 사례 시점까지만 | 답안지에서 넣는다(§11.3) |
| `shadow` | 현재 버전 | 없다 | 현재(그 일감의 노트 제외) | 답안지 또는 사람 |

- 모드는 `run.json` 에 적히고 실행 중에 바뀌지 않는다.
- `replay`·`shadow` 에서는 수집 단계를 뺀 모든 에이전트에서 Atlassian·Slack·GitHub 도구를 허용하지 않고, 게이트 결정을 heka 에 기록하지 않는다.

## 2. 공통 틀

### 2.1 산출물 틀

정본 파일은 모두 같은 겉 구조를 쓴다. 에이전트가 쓰는 것은 `items` 뿐이고 나머지는 코어가 채운다.

| 칸 | 내용 |
|---|---|
| `schema` | 종류와 판(예: `hew.analysis/1`) |
| `run_id`, `stage`, `attempt` | 실행, 단계, 몇 번째 제출인지 |
| `input_revision` | 이 산출물이 읽은 입력의 해시(원천 manifest, 앞 단계 정본, 답) |
| `produced_by` | 역할, 모델, effort, 역할 정의의 git SHA, 세션 id |
| `items` | 단계별 본문(§4, §5, §7) |
| `open` | 아직 닫히지 않은 것의 id 목록(질문, 미결정 차이, 미확인 가정) |
| `verdict` | 결정적 검사와 사수 지적에서 코어가 계산한 판정(`pass`, `blocked`, 사유) |
| `cost` | 이 산출물에 든 실행들의 비용·시간 합 |

### 2.2 id 규칙

heka `hew-id-labels-korean` 을 따른다. 새 종류는 [가정]이다.

| 대상 | 형식 | 대상 | 형식 |
|---|---|---|---|
| 화면 | `화면-n` | 원천 | `S-n` |
| 화면의 상태 변형 | `화면-n.m` | 원문 단위 | `U-n` |
| 요구 | `요구-n` | 범위 장부 행 | `C-n` |
| 인수 조건 | `요구-n/AC-k` | 영향 영역, 막힘 | `I-n`, `B-n` |
| 질문, 차이, 가정 | `Q-n`, `D-n`, `A-n` | 시나리오 | `시나리오-n` |
| 티켓(분해안), PR 묶음 | `Tn`, `PR-n` | 지적 | `F-n` |

### 2.3 근거 형식

근거는 항상 "원문 단위 id + 그 단위에서 그대로 옮긴 인용"이다.

```json
{ "unit_id": "U-41", "quote": "원가가 입력되지 않은 팩은 판매가만 노출한다" }
```

- 코어는 인용이 그 단위의 본문에 실제로 있는지 대조한다(공백과 줄바꿈만 정규화).
- 시안이 근거이면 단위는 Figma 화면이나 설명 카드이고, 인용 대신 `image`(스냅샷 경로)와 필요하면 `box`(좌표)를 쓴다.

### 2.4 revision

- revision 은 승인 대상 전체의 해시다. 대상은 `analysis`(사람용·AI용 문장 모두), `scenarios`, `plan`, `answers`, 원천 manifest 다.
- 계산: 키를 정렬한 JSON 의 sha256. 비용, 시각, 세션 id, 빈 값은 뺀다.
- 승인은 revision 하나를 잠근다. 잠근 뒤 정본이 바뀌면 revision 이 달라지고 승인은 무효다.

### 2.5 명령 출력과 종료 코드

모든 명령은 `--json` 에서 `{ ok, data, warnings[], errors[] }` 를 낸다.

| 코드 | 뜻 |
|---|---|
| 0 | 성공 |
| 2 | 사용법 오류 |
| 3 | 검증 거부(정본과 상태는 바뀌지 않음) |
| 4 | 지금 상태에서는 할 수 없는 명령 |
| 5 | 외부 실패(에이전트 실행, 네트워크) |
| 1 | 그 밖의 내부 오류 |

## 3. 원천과 원문 단위

### 3.1 수집

- `hew init` 이 수집 계획을 만든다. 입력이 PRD URL 이면 PRD 를, Jira 티켓 URL 이면 티켓과 그 상위 스토리·에픽에 연결된 PRD 를 필수 원천으로 둔다.
- `collector` 가 계획대로 가져와 `hew source add` 로 등록한다. 등록할 때 코어가 본문을 파일로 저장하고 해시를 `manifest.json` 에 적는다.
- 본문은 모델이 다시 적지 않는다. 모델이 옮겨 적으면 글자가 바뀌기 때문이다. 코어가 수집 세션의 기록에서 도구가 돌려준 결과를 그대로 꺼내 저장한다. [사실: 옛 hew 의 `toolcalls extract` 가 같은 이유로 이 방식을 썼다]

| 원천 | 가져오는 것 | 필수 |
|---|---|---|
| PRD | Confluence 본문(버전 번호 포함). `live` 는 현재 버전, `replay` 는 사례가 정한 버전 | 예(PRD 경로) |
| 티켓 | Jira 티켓 본문과 상위 스토리·에픽 | 예(작은 티켓 경로) |
| Figma | PRD 에 연결된 파일·페이지의 메타데이터, 앱 화면과 그 AS-IS, 설명 카드의 스크린샷 | PRD 에 링크가 있으면 |
| 관련 문서 | PRD 가 직접 링크한 ADR, 로그 설계 문서 | 아니오 |
| 코드 | 대상 저장소 경로와 base SHA | 예 |
| OpenAPI | 환경별 `openapi.json`(staging, dev-N) | 변경 API 가 있으면 |

- Figma 는 heka `figma-mcp-read-procedure` 를 따른다. 메타데이터는 파일로 받아 코어가 줄 단위 정규식으로 파싱하고, 플랫폼은 프레임 이름 접두사(`앱/`, `app/`, `모웹/`, `웹/`, `web/`)로 가르며, AS-IS·TO-BE 는 라벨 좌표로 짝짓는다. 같은 그림은 해시로 하나만 남긴다.
- AS-IS 는 TO-BE 옆뿐 아니라 "제거 대상 UI" 같은 다른 섹션에서도 찾는다(heka `hew-gate-layout-decisions-2026-11-11` 의 4).
- 수집이 끝나면 코어가 `sources/figma/inventory.json`(프레임 목록, 플랫폼, 좌표, 짝, 스크린샷 경로)을 만든다.

### 3.2 원문 단위

누락 검사를 "통째로 다시 읽기"가 아니라 "단위마다 대조"로 만들기 위해, 코어가 원천을 단위로 쪼갠다. 모델을 쓰지 않는다.

| 원천 | 단위 |
|---|---|
| PRD 의 표 | 행 하나. 열 이름을 함께 싣는다(User Journey, 주체, 요구, 작업 구분 등) |
| PRD 의 본문 | 글머리표 항목 하나 또는 문단 하나 |
| Figma | 앱 레인 화면(프레임) 하나, 설명 카드 하나 |
| 티켓·관련 문서 | 글머리표 항목 하나 또는 문단 하나 |

단위의 칸: `id`, `source_id`, `locator`(절 경로와 행 번호, 또는 노드 id), `kind`, `text`, `columns`(표 행일 때), `actor`(표에 주체 열이 있으면 그 값), `platform`(Figma 일 때), `image`(Figma 일 때).

- `actor` 가 운영자·관리자인 단위는 요구·차이·질문의 근거로 쓸 수 없다(§4.6 의 검사 `evidence_operator_row`). 예외는 작업 구분 표의 Mobile(App) 열에 명시된 요소다(heka `hew-scope-operator-journeys-excluded-2026-10-29`).
- 웹·모웹 레인의 Figma 프레임은 단위로 싣되 `platform` 을 표기하고 요구를 묶지 않는다.
- 표의 주체 열을 코드로 알아내지 못하는 PRD 가 있을 수 있다. 그때는 `actor` 를 비우고 사수가 판정한다(§6.2 의 W6).

## 4. 요구사항 분석 문서(`analysis`)

화면 우선이다. Figma 앱 화면 목록을 먼저 만들고 요구를 화면 아래에 둔다(heka `hew-2026-10-21-figma-prd`). 시안이 없는 일감(작은 티켓 등)은 화면 목록을 코드의 화면으로 만든다.

### 4.1 본문 구성

`items` 는 아래 일곱 묶음이다.

| 묶음 | 내용 |
|---|---|
| `screens` | 화면과 상태 변형, 화면별 이미지 |
| `requirements` | 요구(사람용 문장, AI용 칸, 인수 조건) |
| `deltas` | PRD–Figma 차이와 결정 |
| `questions` | 질문 |
| `assumptions` | 가정 |
| `coverage` | 범위 장부(원문 단위마다 어떻게 처리했는지) |
| `impact` | 코드 수준 영향 분석과 막힐 것 |

### 4.2 화면

| 칸 | 내용 |
|---|---|
| `id`, `name` | `화면-n`, 사람이 읽는 이름 |
| `figma` | 파일 키, 노드 id, 링크. 페이지에는 번호가 아니라 `시안↗` 링크로 보인다 |
| `images[]` | `role`(`as_is`, `to_be`, `both`), 스냅샷 경로, 해시 |
| `variants[]` | 상태 변형(`화면-n.m`, 이름, 이미지). 변형을 별도 화면으로 펼치지 않는다 |
| `code` | 이 화면에 해당하는 코드의 화면 이름과 경로(영향 분석에서 채운다) |
| `change` | `new`, `changed`, `removed`, `reference`(바뀌지 않지만 참고) |

### 4.3 요구

| 칸 | 사람용/AI용 | 내용 |
|---|---|---|
| `id`, `title` | 사람용 | `요구-n`, 한 줄 제목 |
| `screen_ids[]` | 사람용 | 첫 번째가 대표 자리. 비어 있으면 "화면에 묶이지 않은 요구" |
| `changes[]` | 사람용 | 항목 하나가 변경 하나다. `{ text, screen_id }`. 여러 화면·변형에 걸치면 항목마다 자리를 적는다 |
| `status` | 사람용 | `confirmed`, `pending`(열린 질문·미결정 차이·미확인 가정에 걸림) |
| `evidence[]` | 둘 다 | §2.3 형식. 변경 항목마다 근거가 하나 이상 있어야 한다 |
| `acceptance[]` | 사람용(기본 접힘) | `{ id, given?, when, then, verify }`. `verify.method` 는 `unit_test`, `type_check`, `qa_scenario`, `visual_compare`, `review` 중 하나 |
| `ai` | AI용 | 아래 네 칸만 있다 |
| `ai.code[]` | AI용 | `{ path, symbol?, role }`. `role` 은 `modify`, `reuse`, `reference` |
| `ai.verify[]` | AI용 | 인수 조건 id 와 그것을 확인하는 구체적 방법(테스트 파일 위치, 비교할 화면) |
| `ai.rules[]` | AI용 | 적용할 heka 규칙 id |
| `ai.notes[]` | AI용 | 근거 인용이 딸린 보충 `{ text, evidence }`. 근거 없는 보충은 쓸 수 없다 |
| `depends_on[]` | 둘 다 | 먼저 끝나야 하는 요구 |

- 사람이 승인하는 대상은 사람용 칸이다. AI용 칸은 새 동작·조건을 담지 못한다. `ai.notes` 의 문장이 `changes`·`acceptance` 에 없는 동작을 말하면 사수가 지적한다(§6.2 의 W5).
- `confirmed` 는 근거가 모두 대조를 통과했고 걸린 질문·차이·가정이 없을 때만 쓸 수 있다. 근거 없이 "별도 단계일 것"처럼 추정으로 범위를 닫지 않는다. 그런 경우는 질문으로 올린다.
- 숫자가 들어간 변경은 시안의 숫자를 산술로 확인한 결과를 `ai.notes` 에 남긴다(heka `figma-mcp-read-procedure` 의 7).

### 4.4 차이, 질문, 가정

차이(`deltas`)

| 칸 | 내용 |
|---|---|
| `id`, `title`, `kind` | `D-n`, 제목, `figma_only`·`prd_only`·`mismatch` |
| `requirement_ids[]` | 첫 번째가 대표 요구. 페이지는 대표 요구 아래 한 번만 그린다 |
| `comparison` | `{ prd_source, figma_source, rows[{ aspect, prd, figma }] }`. 같은 조건·같은 대상일 때만 한 행에 두고 짝이 없으면 비운다 |
| `prd_evidence`, `figma_evidence` | §2.3 형식의 원문 인용 |
| `audience[]` | `dev`, `po`, `designer`, `backend` |
| `recommendation` | 추천 결정과 이유(선택) |
| `decision` | 사람이 채운다. `follow_figma`, `follow_prd`, `drop`, `hold`. 종류별로 허용되는 값이 다르다(heka `hew-2026-10-21-follow-figma`) |

- 차이 하나에 결정 하나다. 결정이 요구마다 달라질 수 있으면 요구 단위로 나눈다.
- `hold` 는 승인을 막지 않지만 분해안에서 빠지고 보류 사유로 남는다. `drop` 은 범위 장부에 범위 밖으로 기록된다.

질문(`questions`)

| 칸 | 내용 |
|---|---|
| `id`, `text` | `Q-n`, 질문 |
| `origin` | `analysis`, `impact`(막힐 것), `qa`, `sasu`(사수 지적에서 넘어옴) |
| `blocking` | 답이 없으면 진행할 수 없는가 |
| `options[]` | `{ key, label, consequence }`. `consequence` 는 "이 답이 바꾸는 구현"이다 |
| `recommended`, `rationale` | 추천 선택지와 근거(§2.3 형식) |
| `affects` | 걸린 요구·시나리오 id |
| `audience[]` | 차이와 같다 |
| `answer` | 사람이 채운다. 선택지 키 또는 자유 답 |

- 모든 질문은 명시적 답이 있어야 닫힌다. 추천안을 답으로 간주하지 않는다.
- 원문에 이미 답이 있는 것을 묻지 않는다. 사수가 질문마다 원문에 답이 있는지 본다(§6.2 의 W9).

가정(`assumptions`): `id`, `text`, `basis`(근거 또는 근거가 없는 이유), `requirement_ids[]`, `status`(사람이 `confirmed` 또는 `rejected`).

### 4.5 범위 장부와 영향 분석

범위 장부(`coverage`): 원문 단위마다 행이 정확히 하나 있다.

| 칸 | 내용 |
|---|---|
| `id`, `unit_id` | `C-n`, 단위 |
| `disposition` | `covered`, `out_of_scope`, `not_app`(운영자 주체, 웹 레인, 서버 몫), `duplicate`, `context`(배경 설명) |
| `requirement_ids[]` | `covered` 일 때 필수 |
| `quote`, `reason` | `out_of_scope`·`not_app` 일 때 필수. 범위 밖은 원문 인용이 있어야 한다 |
| `delta_id` | `drop` 결정으로 범위 밖이 된 경우 |

영향 분석(`impact`)

| 칸 | 내용 |
|---|---|
| `areas[]` | `{ id, screen_ids, paths[], components[], feature_flag? }` |
| `apis[]` | `{ method, path, fields[], presence{ 환경: 있음/없음 } }`. 환경별 OpenAPI 와 대조한 결과다 |
| `assets[]` | `{ name, exists, path? }`. 시안에 있는 아이콘·그래픽이 저장소에 있는지 |
| `blockers[]` | `{ id, kind, detail, question_id }`. `kind` 는 `missing_asset`, `missing_api`, `missing_field`, `unclear_component`, `other` |
| `environment` | 고른 서버 환경과 근거(설계 §7) |

- 막힐 것은 반드시 질문으로 이어진다. `question_id` 가 없는 막힘은 거부한다.
- 시안의 변경 대상을 코드에서 찾을 때는 AS-IS 문구로 찾는다. Figma 컴포넌트 이름은 코드에 없다(heka `figma-to-mobile-component-lookup`).

### 4.6 결정적 검사

`hew submit analysis` 와 `hew check` 가 돌린다. 거부는 종료 3 이고, 경고는 저장하되 게이트의 "확인 필요"에 올린다.

| 코드 | 검사 | 결과 |
|---|---|---|
| `id_format`, `id_stable` | id 형식. 재제출에서 사라지거나 바뀐 id | 거부 |
| `ref_missing` | 없는 화면·요구·단위·질문을 가리키는 참조 | 거부 |
| `quote_not_found` | 인용이 그 단위 본문에 없다 | 거부 |
| `change_without_evidence` | 근거가 없는 변경 항목 | 거부 |
| `confirmed_with_open` | `confirmed` 인데 열린 질문·차이·가정에 걸려 있다 | 거부 |
| `coverage_incomplete` | 범위 장부에 행이 없는 원문 단위, 행이 둘 이상인 단위 | 거부 |
| `scope_out_without_quote` | 인용 없는 범위 밖 처리 | 거부 |
| `evidence_operator_row` | 주체가 운영자·관리자인 단위를 근거로 썼다 | 거부 |
| `evidence_wrong_lane` | 웹·모웹 레인 프레임만을 근거로 한 앱 요구 | 경고 |
| `blocker_without_question` | 질문으로 이어지지 않은 막힘 | 거부 |
| `ac_missing`, `ac_without_verify` | 인수 조건이 없는 요구, 검증 수단이 없는 인수 조건 | 거부 |
| `ai_note_without_evidence` | 근거 없는 `ai.notes` | 거부 |
| `ai_code_path_missing` | `ai.code` 의 경로가 base SHA 의 저장소에 없다(`role` 이 `modify`·`reuse` 일 때) | 거부 |
| `screen_without_image` | 시안이 있는 일감인데 이미지가 없는 화면 | 경고 |
| `variant_without_change` | 변경 항목이 하나도 걸리지 않은 변형 | 경고 |
| `delta_decision_kind` | 차이 종류에 허용되지 않는 결정 값 | 거부 |

| `mismatch_ratio` | `mismatch` 차이에 걸린 요구 수 / 전체 요구 수. 10%를 넘으면 확인 요청서를 만든다 | 정보 |

## 6. 매니저 사수

### 6.1 원칙

- 사수는 문서 전체를 다시 읽지 않는다. 코어가 만든 작은 작업 단위를 하나씩 판정한다.
- 코드로 할 수 있는 대조는 §4.6·§5 의 결정적 검사가 이미 했다. 사수는 뜻을 봐야 하는 것만 본다.
- 증거(원문 인용이나 이미지 위치)가 없는 지적은 차단하지 않는다.

### 6.2 작업 단위

| 코드 | 단위 | 사수에게 주는 것 | 묻는 것 |
|---|---|---|---|
| W2 | 요구 하나 | 사람용 문장, 근거로 든 단위들의 본문 | 각 변경 항목이 근거로 뒷받침되는가 |
| W3 | 원문 단위 하나 | 단위 본문, 범위 장부의 처리, 그 단위를 근거로 든 요구들 | 이 단위가 말하는 것이 빠짐없이 요구에 있는가. 처리(`not_app` 등)가 맞는가 |
| W4 | `confirmed` 요구 하나 | 요구, 근거 단위들, 같은 절의 이웃 단위들 | 원문에 미정·조건부·논의 필요 표시가 있는데 확정으로 적었는가 |
| W5 | 요구 하나 | 사람용 칸과 `ai.notes` | AI용 문장에만 있는 동작·조건이 있는가 |
| W6 | `actor` 가 빈 표 행 단위 | 행 전체 | 주체가 운영자·관리자인가 |
| W7 | AS-IS·TO-BE 가 있는 화면 하나 | 두 이미지, 코어가 계산한 차이 상자, 그 화면의 변경 항목 | 변경 항목에 없는 시각 차이(아이콘·그래픽·컴포넌트 교체)가 있는가 |
| W8 | 차이 하나 | 비교 행, 양쪽 인용 | 한 행에 놓인 짝이 같은 조건·같은 대상인가 |
| W9 | 질문 하나 | 질문, 관련 단위들 | 원문에 이미 답이 있는가 |

- W1(인용이 원문에 있는가)은 코드 검사 `quote_not_found` 다.
- W7 은 Haiku 5.5 로 되는지 확인되지 않았다(설계 §13 의 2). 결함 주입에서 못 잡으면 이 단위만 상위 모델로 올린다. 차이 상자 계산은 코드다.

### 6.3 실행

- `hew sasu plan` 이 작업 단위를 만들고 묶음 파일로 나눈다. 묶음 하나는 입력 10만 토큰 아래로 유지한다(Haiku 5.5 의 장문 할증 기준).
- 묶음마다 `manager-sasu` 세션 하나를 띄운다. 세션은 묶음 파일만 읽고 `findings` 를 제출한다.
- 같은 종류의 단위끼리 묶는다. 묶음 안의 단위 수는 20개로 시작하고 결함 주입 결과를 보고 조정한다. [가정]

### 6.4 지적(`findings`)

| 칸 | 내용 |
|---|---|
| `id`, `work` | `F-n`, 작업 단위 코드와 대상 id |
| `verdict` | `ok`, `issue` |
| `kind` | `unsupported`, `missing`, `wrong_disposition`, `false_confirmed`, `ai_only_behavior`, `operator_row`, `visual_unlisted`, `bad_pairing`, `already_answered` |
| `claim` | 무엇이 문제인지 한 문장 |
| `evidence` | §2.3 형식. 없으면 차단하지 않는다 |
| `action` | `fix`(테크니컬 매니저가 고침), `ask`(질문으로 올림), `drop`(항목 삭제) |

- 모든 작업 단위에 판정이 하나씩 있어야 한다. 빠진 단위가 있으면 제출을 거부한다.
- 차단 지적이 있으면 코어가 지적 목록을 패킷으로 만들어 테크니컬 매니저를 다시 띄운다. 상한은 2회다.
- 상한에 닿고도 남은 차단 지적은 코어가 `origin: sasu` 질문으로 바꿔 게이트에 올린다. 통과로 치지 않는다.
- 반송 뒤 재확인은 바뀐 항목에 걸린 작업 단위만 다시 돌린다.

## 7. 티켓 분해안(`plan`)과 티켓 사수

### 7.1 본문

`ticket-maker` 가 답이 반영된 `analysis` 와 규칙 파일을 읽고 만든다. Jira 에 쓰지 않는다.

티켓(`tickets[]`)

| 칸 | 내용 |
|---|---|
| `id` | `Tn` |
| `title` | `[MO] {일감명} / {작업 요약}` (heka `jira-ticket-title-format`) |
| `body` | `배경`, `작업 내용`, 필요하면 `확인 사항`·`선행 의존`, `참고` 순서(heka `jira-mo-ticket-body-format`). 코드 경로와 구현 방법은 쓰지 않는다 |
| `requirement_ids[]`, `changes[]` | 덮는 요구와, 요구의 일부만 덮을 때 그 변경 항목 |
| `sp` | Story Points. 1SP 는 1시간이다 |
| `depends_on[]` | 먼저 끝나야 하는 티켓 |
| `pr` | 속한 PR 묶음 |

PR 묶음(`prs[]`): `id`, `title`, `ticket_ids[]`, `base`(`develop` 또는 앞선 `PR-n`), `order`.

그 밖: `parent`(티켓을 달 스토리 키), `feature_flag{ used, name, removal_ticket }`, `excluded[]`(보류 결정으로 빠진 항목과 사유).

### 7.2 분해 규칙

`rules/plan.yaml` 에 두고 코드로 검사한다. 값은 heka 규칙에서 가져왔고 [가정]이다.

- 티켓은 2~4SP 를 기본으로 한다. 넘으면 나눈다(heka `prd-to-pr-pipeline-decisions-2026-09-r2`).
- 티켓 하나가 PR 하나일 필요는 없다. 함께 리뷰해야 뜻이 통하는 티켓은 한 PR 로 묶는다(2026-10-20 결정 6, APP-3008 실제 작업).
- 피처플래그를 쓰는 일감은 에픽 브랜치를 만들지 않는다. 첫 PR 의 base 는 `develop` 이고 의존이 있으면 앞 PR 위에 쌓으며, 플래그 제거가 마지막 티켓이다(heka `app-team-feature-flag-replaces-epic-branch`).
- PR 하나의 예상 변경 크기에 상한을 둔다. 값은 [미결]이다(이 저장소의 PR 크기 중앙값은 68줄이다).

### 7.3 결정적 검사

| 코드 | 검사 | 결과 |
|---|---|---|
| `requirement_unmapped` | 범위 안 요구(변경 항목 단위) 중 어느 티켓에도 없는 것 | 거부 |
| `ticket_orphan` | 요구에 걸리지 않은 티켓(플래그 제거 티켓은 예외) | 거부 |
| `hold_included` | 보류 결정 항목이 티켓에 들어 있다 | 거부 |
| `title_format`, `body_sections` | 제목 형식, 본문 절 구성 | 거부 |
| `body_code_detail` | 본문에 파일 경로, 줄 번호, 함수 이름이 있다 | 거부 |
| `dependency_cycle` | 티켓·PR 의존에 순환이 있다 | 거부 |
| `pr_base_order` | PR 의 base 와 순서가 티켓 의존과 어긋난다 | 거부 |
| `flag_removal_last` | 플래그를 쓰는데 제거 티켓이 없거나 마지막이 아니다 | 거부 |
| `sp_range` | 2~4SP 를 벗어난 티켓 | 경고 |
| `requirement_dependency_broken` | 요구의 의존 순서가 티켓 순서에서 뒤집혔다 | 거부 |

### 7.4 티켓 사수

작업 단위는 티켓 하나다. 티켓 본문과 그 티켓이 덮는 요구(사람용 문장)를 주고 두 가지를 묻는다.

- 티켓이 요구와 모순되거나 요구에 없는 일을 시키는가.
- 티켓만 읽은 사람이 무엇을 해야 하는지 알 수 있는가(맥락 누락).

지적 형식과 반송(상한 2회)은 §6.4 와 같다. 반송은 티켓 메이커에게 간다.

## 8. 게이트

### 8.1 페이지

`hew gate build` 가 정본에서 `gate/page.html` 과 올릴 이미지 목록을 만든다. 페이지는 heka 에 남은 게이트 결정을 따른다.

| 영역 | 내용 | 근거 |
|---|---|---|
| 머리 | 일감, 원천 버전, 진행(질문 n개 중 m개), 서버 환경, 승인 버튼 | 설계 §5.1 |
| 확인 필요 | 결정적 검사의 경고, 다시 답해야 하는 질문 | — |
| 화면 | 화면별 탭. 탭 안에서 AS-IS·TO-BE 이미지는 왼쪽에 고정하고 요구는 오른쪽에서 스크롤한다. 이미지 폭 250px. 차이는 붉은 상자(선 2px, 불투명도 0.8), 차이 면적이 60%를 넘으면 "전면 변경"으로 표시한다 | `hew-gate-layout-decisions-2026-11-11`, `hew-6-2026-10-23-mismatch` |
| 요구 | 화면 아래에 요구별 변경 목록. 변형에 걸린 변경은 그 변형 아래. 인수 조건은 기본 접힘. AI용 칸은 "AI용 보기"로 접어 둔다 | `hew-2026-10-21-figma-prd` |
| 차이 | 대표 요구 아래 한 번만. 관점, PRD, 시안 3열 표. 미결정은 펼치고 결정된 것은 접는다. 다른 관련 요구에는 링크만 | `hew-2026-10-21-requirement-ids`, `hew-delta-comparison-rows-2026-10-28` |
| 질문 | 선택지, 추천과 근거, "이 답이 바꾸는 구현", 자유 답 | 설계 §5.1 |
| 가정과 범위 밖 | 가정 확인. 범위 밖은 원문 인용과 함께 | 설계 §5.1 |
| 영향 분석 | 걸리는 영역, API 의 환경별 유무, 없는 에셋 | 설계 §5.1 |
| QA 시나리오 | 시나리오별 여정, 기대 결과, 실서버/모킹 전환 | 설계 §5.1 |
| 분해안 | 티켓 표(제목, 덮는 요구, SP), PR 묶음, 의존 그래프, 수정 요청 입력. 답변 단계에서는 "답이 끝나면 만들어집니다"로 비워 둔다 | 설계 §4.4 |

- 기계 식별자(Figma 노드 번호, 원문 단위 id)는 화면에 그대로 보이지 않는다. 링크나 접힌 상세로만 간다.
- 링크로 이동한 뒤 원래 자리로 돌아올 수 있어야 한다.
- 화면에 보이는 문장은 사람용 칸에서만 가져온다.

### 8.2 페이지가 저장하는 것

페이지는 Artifact 의 데이터베이스에 쓴다. 문서 id 는 항목 id 다.

| 컬렉션 | 문서 | 내용 |
|---|---|---|
| `answers` | `Q-n` | `{ option?, text?, at, by }` |
| `scope` | `D-n` | `{ decision, note?, at, by }`. 결정을 바꾸면 메모는 지워진다 |
| `assumptions` | `A-n` | `{ status, note?, at, by }` |
| `scenarios` | `시나리오-n` | `{ backend, note?, at, by }` (실서버/모킹을 바꿨을 때만) |
| `plan_requests` | 자동 id | `{ target, text, at, by }`. `target` 은 `Tn`, `PR-n`, `전체` |
| `approvals` | revision 앞 12자 | `{ revision, at, by, note? }`. 문서 id 가 revision 이라 다른 판의 승인과 섞이지 않는다. 승인을 거두면 문서를 지운다 |
| `meta` | `current` | `{ revision, answered, total, updated_at }` (세션 스킬이 진행을 볼 때 쓴다) |

### 8.3 두 번 보는 절차

1. 답변: 사람이 질문에 답하고, 차이를 결정하고, 가정을 확인하고, 필요하면 모킹을 바꾼다.
2. 세션 스킬이 답을 내려받아 `hew gate import` 로 넘긴다. 코어는 `answers.json` 에 합치고, 모두 채워졌으면 `answers_complete` 로 간다.
3. 코어가 테크니컬 매니저와 QA 설계를 "답 반영" 패킷으로 다시 띄운다. 요구의 `pending` 이 `confirmed` 로 바뀌고, 범위 밖·보류가 정리된다. 바뀐 항목만 사수가 다시 본다.
4. 답 반영에서 새 질문이 생기면 페이지를 다시 게시하고 1로 돌아간다.
5. 티켓 메이커와 티켓 사수가 돈다. 분해안이 실린 페이지를 같은 주소에 다시 게시한다.
6. 승인: 사람이 분해안을 확인한다. 수정 요청을 적으면 5로 돌아간다. 승인 버튼은 열린 항목이 없고 페이지의 revision 이 최신일 때만 켜진다.
7. 세션 스킬이 승인 문서를 내려받아 `hew approve` 를 부른다. 코어는 revision 이 현재 값과 같을 때만 잠근다.

- 답의 시각이 이전 답보다 늦은 것만 새 답으로 본다.
- 승인하면 게이트에서 내린 결정을 heka 결정 노트로 남긴다(`live` 모드만). 차이 결정과 차단 질문의 답은 건별로, 나머지는 묶어서 남긴다(heka `hew-6-2026-10-23-mismatch` 의 4).

### 8.4 확인 요청서

`mismatch_ratio` 가 10%를 넘으면 PO·디자이너에게 보낼 확인 요청서 페이지를 함께 만든다. 대상(`audience`)이 `po`·`designer` 인 질문과 차이만 싣고, 선택지는 게이트와 같다. 요청서에서 고른 답은 세션 스킬이 게이트의 같은 문서로 복사한다(heka `hew-review-request-page-decisions-2026-10-28`). 요청서는 게이트를 대신하지 않는다.

### 8.5 게시와 답 읽기

- 기본은 대화형 세션의 `hew-gate` 스킬이다. 스킬이 하는 일은 넷뿐이다. `hew run` 을 띄워 놓고 기다리기, 페이지와 이미지를 Artifact 로 게시하기, 데이터베이스를 내려받아 `hew gate import`·`hew approve` 부르기, 상태를 사람에게 알리기.
- 무인 세션에서 Artifact 게시와 데이터베이스 읽기가 되면 이 일도 코어가 띄운 세션으로 옮길 수 있다. [미결: 실측, 설계 §13 의 1]
- `replay` 모드는 페이지를 게시하지 않는다. 페이지 파일은 만들어 두고(생성기 검증용) 답은 답안지에서 넣는다.

## 9. 코어 명령

| 명령 | 하는 일 | 상태 변화 |
|---|---|---|
| `hew init --prd <url>` 또는 `--ticket <url>` `[--mode live\|replay\|shadow] [--case <파일>] [--repo <경로>] [--base <브랜치>]` | 실행 폴더와 수집 계획을 만든다 | → `init` |
| `hew run --run <폴더> [--until <상태>]` | 상태를 보고 다음 역할을 띄우는 일을 사람 차례가 올 때까지 되풀이한다 | 간접 |
| `hew next --run <폴더>` | 다음에 할 일을 JSON 으로 알려 준다. 아무것도 바꾸지 않는다 | 없음 |
| `hew status --run <폴더>` | 상태, 열린 항목, 단계별 비용 | 없음 |
| `hew source add\|list\|request` | 원천 등록, 목록, 추가 수집 요청 | 필수 원천이 다 차면 → `collected` |
| `hew units --run <폴더>` | 원문 단위를 열거한다(수집 끝에 자동으로 돈다) | 없음 |
| `hew submit <analysis\|scenarios\|plan\|findings> --file <경로> [--withdraw <id,…>]` | 검증하고 정본에 쓴다 | 단계별 |
| `hew check --run <폴더> [--only <종류>]` | 결정적 검사만 다시 돌린다 | 없음 |
| `hew sasu plan --run <폴더> --for <analysis\|plan>` | 사수 작업 단위와 묶음을 만든다 | 없음 |
| `hew packet --run <폴더> --role <역할>` | 그 역할의 패킷을 만든다(`hew run` 이 내부에서 쓴다) | 없음 |
| `hew gate build --run <폴더> [--review-request]` | 게이트 페이지와 이미지 목록을 만든다 | 없음 |
| `hew gate import --run <폴더> --file <db 내보내기>` | 답·결정·수정 요청을 들여온다 | → `answers_complete` 등 |
| `hew approve --run <폴더> --revision <해시>` | revision 이 같으면 잠근다 | → `approved` |
| `hew mistake add --run <폴더> …` | 실수 기록을 덧붙인다 | 없음 |
| `hew replay prepare\|answer\|judge`, `hew eval inject` | §11 | — |

- 패킷은 역할이 읽어야 할 파일 경로, 이번 일의 범위(처음인지, 반송인지, 답 반영인지), 따를 규칙 id, 제출 방법만 담는다. 앞 단계 에이전트의 추론이나 대화는 담지 않는다.
- 따를 규칙의 본문은 코어가 패킷에 싣는다. [가정] `rules/heka.<역할>.yaml` 에 역할별 규칙 id 를 두고(출발점은 설계 §16), 코어가 heka 명령줄 도구(`node ~/heka/bin/heka.js expand <id>`)로 제목과 "적용" 절을 읽어 넣는다. `replay` 에서는 `--known-at` 으로 사례 시점 이후의 노트를 뺀다. [사실: 옛 hew 의 기준선 주입 훅이 이 방식으로 동작했다]

## 10. 작은 티켓 경로

입력이 Jira 티켓 URL 이면 같은 상태 기계를 돌되 내용이 줄어든다. [가정]

- 원천은 티켓과 상위 스토리이고, 연결된 PRD·Figma 가 있으면 함께 수집한다.
- 시안이 없으면 화면 목록은 코드의 화면에서 만들고 이미지와 차이 표는 없다.
- 분해안은 보통 티켓 1개, PR 1개다. 입력 티켓 자체가 구현 단위이면 새 티켓을 만들지 않고 그 티켓을 `Tn` 으로 쓴다.
- 질문과 차이가 하나도 없어도 승인은 받는다. 이때 게이트는 요구, 인수 조건, 시나리오, 분해안을 한 화면에 보이고 답변 단계를 건너뛴다.
- 한 줄 변경 같은 일감에 게이트 왕복이 과한지는 실제로 돌려 보고 정한다. [미결: 설계 §13 의 10]

## 11. 평가

### 11.1 사례 파일

```yaml
id: app-3008
story: APP-3008
known_at: 2026-09-10            # 이 시점까지의 지식만 쓴다
prd: { page_id: "1000000001", version: 22 }
figma: { url: "…", note: "현재본만 읽을 수 있음" }
repo: { path: "~/Projects/mobile-app", base: "<계산한 SHA>" }
block:
  jira: ["parent = APP-3008"]    # 읽지 못하게 할 티켓
  prs: [1054, 1081, 1091]
  heka_scope: ["ticket/APP-3008"]
  heka_ids: ["app-3008-hew-vs-actual-2026-10-08", "…"]
answers: ./app-3008.answers.yaml # 답안지
gold: ../gold/app-3008.yaml      # 실행 폴더와 에이전트가 볼 수 없는 곳
role: dev                        # dev(프롬프트를 고치며 본 사례) | heldout(채점 전용)
```

- base 는 PR 의 `base.sha` 가 아니라 first-parent 이력에서 계산한다(heka `github-pr-base-sha-not-creation-time-r2`).
- PRD 버전은 날짜로만 고르지 않는다. 사람이 티켓을 쪼갠 시점에 본 버전을 확인한다(heka `confluence-version-history-via-atlassian-mcp-prd-d9-r3`).

### 11.2 컨텍스트 차단

`hew replay prepare` 가 준비하고, 실행기가 지킨다. 설계 §10 의 결정 22·23 이다.

| 대상 | 방법 |
|---|---|
| 코드 | 대상 저장소를 base SHA 로 꺼내 이력이 없는 단일 커밋 사본으로 만든다. 에이전트는 이 사본만 읽는다 |
| PRD·티켓 | 수집 단계가 사례의 버전만 가져온다. 수집 단계 말고는 Atlassian 도구가 없다 |
| heka | 에이전트에 heka 도구를 주지 않는다. 규칙 본문은 코어가 사례 시점(`--known-at`)으로 읽어 패킷에 싣고, 차단 id·범위의 노트는 뺀다 |
| 세션에 자동으로 붙는 heka 주입 | 역할 세션을 사용자 설정 없이 띄우므로(§1.4) 붙지 않는다. 수집 세션에는 붙지만 수집은 정해진 원천만 가져온다 |
| 과거 세션 기록, 메모리 | 읽기 경로를 실행 폴더와 저장소 사본으로 제한하는 훅으로 막는다 |
| 채점표 | 실행 폴더 밖에 두고 위 읽기 제한으로 막는다 |
| 외부 쓰기 | 쓰기 단계를 띄우지 않는다. 게이트 페이지를 게시하지 않고 heka 에 기록하지 않는다 |

- 훅이 입력을 바꾸고 호출을 거부하는 것은 2026-11-13 실험에서 확인했다(설계 §4.3).
- 차단이 실제로 지켜졌는지는 실행 뒤 코어가 세션 기록에서 도구 호출을 훑어 확인한다. 범위 밖 읽기가 하나라도 있으면 그 실행은 채점하지 않는다.
- Figma 는 과거 버전을 읽는 수단을 확인하지 못했다. 사례마다 "현재 시안이 당시와 달라진 곳"을 사람이 적어 두고 채점에서 뺀다. [가정]

### 11.3 답안지

리플레이는 사람 없이 승인까지 가야 한다. 사례마다 실제로 내려졌던 결정을 답안지로 적어 둔다.

- 답안지는 "이런 내용을 물으면 이렇게 답한다"의 목록이다. 질문 id 가 실행마다 달라지므로 내용으로 맞춘다.
- `hew replay answer` 가 질문·차이·가정을 답안지와 맞춘다. 맞추는 일은 모델이 하고(채점용 모델), 맞춘 결과는 기록에 남긴다.
- 답안지에 없는 질문은 "답 없음"으로 기록하고 그 질문에 걸린 요구는 보류로 둔다. 답 없음의 수는 질문 수율 지표에 쓴다.
- 분해안은 수정 요청 없이 승인한 것으로 친다.

### 11.4 채점표와 지표

채점표(gold)는 Claude 가 실제 결과물(티켓, PR, QA 결함)에서 초안을 만들고, 사용자가 에이전트 산출물을 보기 전에 교정한다(heka `hew-slice1-decisions-2026-10-20`). 교정 전 초안으로는 채점하지 않는다.

채점표의 내용: 기준 요구 목록(`must` 여부, 화면, 출처), 반드시 물었어야 할 질문, 당시 확정이 아니었던 항목, 실제 티켓과 PR 묶음, QA 결함과 그 원인.

| 지표 | 정의 | 방향 |
|---|---|---|
| 요구 재현율 | 기준 요구(`must`) 중 산출물의 변경 항목이 덮은 비율 | 높을수록 |
| 지어낸 요구 | 산출 요구 중 기준 요구에도 원문에도 근거가 없는 것의 수 | 0 |
| 틀린 확정 | `confirmed` 인데 채점표와 어긋나는 요구의 수 | 0 |
| 추정으로 닫은 범위 | 질문 없이 범위 밖으로 처리했는데 실제로는 범위 안이었던 것의 수 | 0 |
| 필수 질문 포착률 | 반드시 물었어야 할 질문 중 실제로 물은 비율 | 높을수록 |
| 헛질문 비율 | 원문에 이미 답이 있던 질문의 비율 | 낮을수록 |
| 분해 일치 | 실제 PR 묶음과의 차이(참고 지표) | — |
| 실행당 비용·시간 | `costs.jsonl` 합 | 낮을수록 |

- 대응 판정(산출 요구가 기준 요구를 덮는가)은 채점용 모델이 한다. 채점 모델에게는 두 목록을 섞어 중립 id 로만 보이고, 어느 쪽이 산출물이고 어느 쪽이 채점표인지 알리지 않는다. 사례마다 사람이 일부를 직접 판정해 채점 모델과 맞는지 확인한다. 어긋남이 10%를 넘으면 채점 지시문을 고친다. [가정]
- 실행은 비결정적이므로 사례·구성마다 3회 돌린다.
- 게이트 체류 시간은 리플레이로 잴 수 없다. `live` 실행에서만 기록한다.

### 11.5 결함 주입

`hew eval inject` 가 통과한 정본을 복사해 결함을 심고, 사수만 다시 돌린다.

| 주입 | 잡아야 하는 작업 단위 |
|---|---|
| 요구 하나를 지우고 범위 장부 행을 `context` 로 바꾼다 | W3 |
| 변경 항목 하나를 원문과 다르게 바꾼다(숫자, 조건) | W2 |
| 미정 표시가 있는 요구를 `confirmed` 로 바꾼다 | W4 |
| `ai.notes` 에 사람용 문장에 없는 조건을 넣는다 | W5 |
| 아이콘이 바뀐 화면에서 그 변경 항목을 지운다 | W7 |
| 다른 조건의 두 문장을 한 비교 행에 놓는다 | W8 |

지표는 포착률(심은 결함 중 잡은 비율)과 오탐률(결함을 심지 않은 원본에서 낸 차단 지적 중 사람이 틀렸다고 본 비율)이다. 주입 한 건에 결함 하나만 심는다.

### 11.6 완료 기준

1번 단계는 아래를 채우면 끝난 것으로 보고 2번 단계 이후로 넘어간다. 수치는 [제안]이고, 기준선(옛 hew 의 분석 결과나 첫 실행)을 잰 뒤 사용자가 확정한다.

| 기준 | 제안값 |
|---|---|
| 요구 재현율(`must`) | 사례마다 3회 평균 95% 이상, 3회 중 2회 이상 100% |
| 틀린 확정, 추정으로 닫은 범위 | 모든 실행에서 0 |
| 지어낸 요구 | 실행당 1건 이하 |
| 필수 질문 포착률 | 90% 이상 |
| 헛질문 비율 | 20% 이하 |
| 사수 포착률, 오탐률 | 주입 종류마다 90% 이상, 10% 이하. W7 은 따로 본다 |
| 채점 전용 사례 | 위 기준을 채점 전용 사례 1건 이상에서도 채운다 |
| 컨텍스트 차단 | 채점한 모든 실행에서 범위 밖 읽기 0 |

- 사례: APP-3008, APP-2513 은 실패 내용이 설계와 heka 규칙에 이미 들어 있어 `dev` 로만 쓴다. 두 사례의 채점표 초안이 옛 hew 에 있으나 사용자 교정 전이라 그대로는 채점에 쓰지 못한다. [사실] `heldout` 사례는 사용자가 고른다. [미결] 후보는 이 워크플로우 설계에 쓰이지 않은 과거 PRD 다.
- 모델 비교(설계 §4.5): 같은 사례를 Opus 5.5 `high` 와 Fable 5.2 `medium` 으로 각각 3회 돌려 요구 재현율과 틀린 확정을 견준다. 차이가 실행 간 흔들림보다 작으면 싼 쪽을 쓴다.

## 12. 실수 기록

`mistakes.jsonl` 에 한 줄씩 덧붙인다. 개선 루프는 나중에 만들지만 형식은 지금 정한다(설계 원칙 9).

| 칸 | 내용 |
|---|---|
| `id`, `run_id`, `at` | 식별자, 실행, 시각 |
| `found_stage`, `cause_stage` | 발견된 단계, 원인이 된 단계 |
| `found_by` | `check`(결정적 검사), `sasu`, `human_gate`, `replay_judge`, `review`, `qa`, `post`(사후 지적) |
| `type` | `missing_requirement`, `invented_requirement`, `false_confirmed`, `scope_closed_by_guess`, `wrong_evidence`, `visual_missed`, `needless_question`, `missed_question`, `bad_plan`, `format`, `other` |
| `target` | 걸린 항목 id |
| `evidence` | 무엇을 보고 실수로 판정했는지 |
| `versions` | 그때의 역할 정의 git SHA, 모델, effort, 코어 버전 |
| `case` | 이 실수를 회귀 사례로 만들었으면 그 id |

- 사수의 차단 지적이 받아들여져 고쳐지면 코어가 자동으로 기록한다. 게이트에서 사람이 요구를 고치게 한 것, 리플레이 채점에서 나온 것도 자동으로 기록한다.
- 역할 정의를 고쳐 규칙을 하나 넣을 때는 그 규칙을 낳은 실수의 `case` 가 있어야 한다.

## 13. 구현 순서

구현은 하위 모델 에이전트에 맡기고, 명세와 검증은 상위 모델이 한다. 조각마다 끝났는지 확인하는 방법을 먼저 적는다.

| 조각 | 내용 | 끝난 것으로 보는 조건 |
|---|---|---|
| 0 | 실측(§14) | 끝남(2026-11-14). 3번만 미결 |

## 14. 실측과 미결

구현 전에 작은 실험으로 확인한 것(조각 0, 2026-11-14, Claude Code 2.1.323, Haiku 5.5)

| # | 확인할 것 | 결과 |
|---|---|---|
| 1 | `--agent`·`--plugin-dir` 로 역할 정의가 실리고 `--allowedTools`·`dontAsk` 로 의도한 도구만 쓰이는가 | 된다. 역할 정의의 `tools` 에 적은 도구만 세션에 실렸다. `dontAsk` 에서 허용하지 않은 Bash 명령은 거부됐다. 다만 Read 는 경로를 가리지 않으므로 경로 훅이 필요하다(7번) |
| 2 | 무인 세션에서 Atlassian·Figma 읽기 도구가 보이는가 | 보인다. Atlassian 은 처음부터 실려 있고(`mcp__claude_ai_Atlassian__*`), Figma 는 ToolSearch 로 찾은 뒤 호출됐다(`mcp__claude_ai_Figma__*`) |
| 3 | 사용량 한도에 걸린 `claude -p` 가 어떻게 끝나는가 | 확인하지 못했다. 일부러 한도에 걸 수 없다. 처음 걸렸을 때의 출력을 기록해 구분 규칙을 만든다. 그 전에는 실패를 모두 같은 재시도로 다룬다 [미결] |
| 4 | 사수 세션 하나의 고정 비용 | 약 $0.001(도구 2개, 사용자 설정 없음). 묶음 크기는 비용이 아니라 판정 품질로 정한다 |
| 5 | 무인 세션에서 Artifact 게시와 데이터베이스 읽기가 되는가 | 하지 않았다. 이 계정은 요청 없이 Artifact 를 게시하지 않기로 했다. 게이트 게시는 세션 스킬이 맡는다(§8.5) |
| 6 | 평가 실행에서 사용자 설정의 heka 주입 훅과 heka 도구를 끄는 방법 | `--setting-sources project,local --strict-mcp-config --mcp-config '{"mcpServers":{}}'` 로 꺼진다. 훅 0번, MCP 0개, 로그인 유지 |
| 7 | 읽기 경로를 제한하는 훅 | Read 는 막힌다(범위 밖 절대 경로, `..` 경로 모두 거부). Grep·Glob 도구는 이 버전에 없어 대상이 아니다. Bash 는 허용 명령 목록과 경로 검사로 막는다(구현 조각 8 에서 확인) |
| 8 | Atlassian 읽기 호출에서 입력 교체 훅이 동작하는가 | 동작한다. `APP-1` 을 조회하라고 시킨 세션에서 훅이 넣은 `APP-3008` 이 조회됐다. 설계 §4.3 의 쓰기 전용 단계는 그대로 간다 |

- 부수 확인: Atlassian 커넥터가 폐기 예정인 V1 주소를 쓰고 있다는 안내가 도구 응답에 실려 온다(2027-03-01 폐기). 커넥터를 다시 추가해야 한다.
