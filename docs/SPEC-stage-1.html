§0범위

§0.1다루는 것

설계 문서 §12 의 "1번 단계"다. 입력(PRD URL 또는 Jira 티켓 URL)에서 사람의 승인까지, 그리고 이 구간의 완료 기준을 재는 평가 장치다.

입력 → [0] 수집 → [1] 분석(테크니컬 매니저) → [1] QA 설계 → [1-1] 매니저 사수
     → 게이트(답변) → 답 반영 → [2] 티켓 메이커 → [2-1] 티켓 사수 → 게이트(승인) → 잠금
  • 수집, 원문 단위 열거
  • 요구사항 분석 문서, QA 시나리오, 티켓 분해안의 스키마와 결정적 검사
  • 매니저 사수, 티켓 사수의 작업 단위와 지적 형식
  • 게이트 페이지와 답·결정·승인의 저장 형식
  • 코어 명령 계약, 상태 기계, 에이전트 실행기
  • 리플레이, 결함 주입, 채점, 완료 기준
  • 실수 기록 형식

§0.2다루지 않는 것

Jira 쓰기 단계, 빌더, 빌더 사수, 코드 리뷰, QA 실행, PR 작성, 승인 뒤 요구 변경 처리, 종료 보고서. 다만 이 단계들이 읽을 산출물의 형식은 여기서 정한다.

§1.4에이전트 실행기

코어의 hew run 이 상태를 보고 다음 역할을 새 세션으로 띄운다.

claude -p "<패킷 경로를 읽고 수행하라는 고정 문장>" \
  --agent <역할> --plugin-dir <hew> \
  --model <모델> --effort <effort> \
  --permission-mode dontAsk --allowedTools <역할별 목록> \
  --settings <실행용 설정(훅)> --output-format json
  • --bare 는 쓰지 않는다. 구독 로그인을 읽지 않기 때문이다. 사실headless 문서 "bare mode doesn't use your subscription login"
  • 결과 JSON 에서 total_cost_usd, num_turns, session_id, 오류 여부를 costs.jsonl 에 남긴다.
  • 세션이 끝나면 코어가 상태를 다시 읽는다. 기대한 제출이 없으면 그 실행은 실패다. 같은 역할을 최대 2회 더 띄우고, 그래도 없으면 실행을 멈추고 사람에게 알린다(승인 전이므로 사람이 세션에 있다). 가정
  • 사용량 한도로 실패하면 리셋 시각까지 기다렸다 같은 역할을 다시 띄운다. 한도 실패를 어떻게 구분하는지는 미결실측.

  • Figma 는 수집 단계가 화면 목록과 스크린샷을 넣어 두되, 분석 중 더 봐야 할 노드가 있으면 테크니컬 매니저가 hew source request 로 요청하고 수집 단계가 한 번 더 돈다. 가정 분석 에이전트에 Figma 도구를 직접 주는 안은 호출 한도와 스냅샷 밖 인용 문제 때문에 택하지 않았다.
  • 쓰기 범위는 실행용 설정의 훅(PreToolUse)이 지킨다. work/<실행 id>/ 밖에 쓰는 호출과 대상 저장소를 바꾸는 명령은 거부한다.
  • Fable 5.2 를 medium 으로 쓸 때는 역할 정의에 "끝까지 진행" 문구를 넣는다(설계 §4.5).

§1.5제출과 검증

  • 에이전트는 초안을 work/ 에 쓰고 hew submit <종류> --file <경로> 를 부른다.
  • 코어는 스키마, 참조 무결성, 결정적 검사를 돌린다. 거부(종료 3)면 정본은 그대로이고 오류 목록을 돌려준다. 에이전트는 같은 세션에서 고쳐 다시 낸다.
  • 통과하면 코어가 공통 틀(§2.1)을 씌워 doc/ 에 쓰고 이벤트를 남긴다.
  • 게이트에 한 번이라도 게시된 뒤의 재제출에서는 사람이 답했거나 결정한 항목을 에이전트가 지우지 못한다. 지우려면 --withdraw <id> 로 명시하고, 사람 입력이 있는 항목은 거부한다(heka hew-submit-withdraw-2026-10-29).
  • 재제출에서 같은 항목은 같은 id 를 유지한다.

§2.3근거 형식

근거는 항상 "원문 단위 id + 그 단위에서 그대로 옮긴 인용"이다.

{ "unit_id": "U-41", "quote": "원가가 입력되지 않은 팩은 판매가만 노출한다" }
  • 코어는 인용이 그 단위의 본문에 실제로 있는지 대조한다(공백과 줄바꿈만 정규화).
  • 시안이 근거이면 단위는 Figma 화면이나 설명 카드이고, 인용 대신 image(스냅샷 경로)와 필요하면 box(좌표)를 쓴다.

§2.4revision

  • revision 은 승인 대상 전체의 해시다. 대상은 analysis(사람용·AI용 문장 모두), scenarios, plan, answers, 원천 manifest 다.
  • 계산: 키를 정렬한 JSON 의 sha256. 비용, 시각, 세션 id, 빈 값은 뺀다.
  • 승인은 revision 하나를 잠근다. 잠근 뒤 정본이 바뀌면 revision 이 달라지고 승인은 무효다.

§3.2원문 단위

누락 검사를 "통째로 다시 읽기"가 아니라 "단위마다 대조"로 만들기 위해, 코어가 원천을 단위로 쪼갠다. 모델을 쓰지 않는다.

원천단위

PRD 의 본문글머리표 항목 하나 또는 문단 하나

§8.3두 번 보는 절차

  1. 답변: 사람이 질문에 답하고, 차이를 결정하고, 가정을 확인하고, 필요하면 모킹을 바꾼다.
  2. 세션 스킬이 답을 내려받아 hew gate import 로 넘긴다. 코어는 answers.json 에 합치고, 모두 채워졌으면 answers_complete 로 간다.
  3. 코어가 테크니컬 매니저와 QA 설계를 "답 반영" 패킷으로 다시 띄운다. 요구의 pending 이 confirmed 로 바뀌고, 범위 밖·보류가 정리된다. 바뀐 항목만 사수가 다시 본다.
  4. 답 반영에서 새 질문이 생기면 페이지를 다시 게시하고 1로 돌아간다.
  5. 티켓 메이커와 티켓 사수가 돈다. 분해안이 실린 페이지를 같은 주소에 다시 게시한다.
  6. 승인: 사람이 분해안을 확인한다. 수정 요청을 적으면 5로 돌아간다. 승인 버튼은 열린 항목이 없고 페이지의 revision 이 최신일 때만 켜진다.
  7. 세션 스킬이 승인 문서를 내려받아 hew approve 를 부른다. 코어는 revision 이 현재 값과 같을 때만 잠근다.
  • 답의 시각이 이전 답보다 늦은 것만 새 답으로 본다.
  • 승인하면 게이트에서 내린 결정을 heka 결정 노트로 남긴다(live 모드만). 차이 결정과 차단 질문의 답은 건별로, 나머지는 묶어서 남긴다(heka hew-6-2026-10-23-mismatch 의 4).

§8.4확인 요청서

mismatch_ratio 가 10%를 넘으면 PO·디자이너에게 보낼 확인 요청서 페이지를 함께 만든다. 대상(audience)이 po·designer 인 질문과 차이만 싣고, 선택지는 게이트와 같다. 요청서에서 고른 답은 세션 스킬이 게이트의 같은 문서로 복사한다(heka hew-review-request-page-decisions-2026-10-28). 요청서는 게이트를 대신하지 않는다.

§8.5게시와 답 읽기

  • 기본은 대화형 세션의 hew-gate 스킬이다. 스킬이 하는 일은 넷뿐이다. hew run 을 띄워 놓고 기다리기, 페이지와 이미지를 Artifact 로 게시하기, 데이터베이스를 내려받아 hew gate import·hew approve 부르기, 상태를 사람에게 알리기.
  • 무인 세션에서 Artifact 게시와 데이터베이스 읽기가 되면 이 일도 코어가 띄운 세션으로 옮길 수 있다. 미결실측, 설계 §13 의 1
  • replay 모드는 페이지를 게시하지 않는다. 페이지 파일은 만들어 두고(생성기 검증용) 답은 답안지에서 넣는다.

§10작은 티켓 경로

입력이 Jira 티켓 URL 이면 같은 상태 기계를 돌되 내용이 줄어든다. 가정

  • 원천은 티켓과 상위 스토리이고, 연결된 PRD·Figma 가 있으면 함께 수집한다.
  • 시안이 없으면 화면 목록은 코드의 화면에서 만들고 이미지와 차이 표는 없다.

§11.4채점표와 지표

채점표(gold)는 Claude 가 실제 결과물(티켓, PR, QA 결함)에서 초안을 만들고, 사용자가 에이전트 산출물을 보기 전에 교정한다(heka hew-slice1-decisions-2026-10-20). 교정 전 초안으로는 채점하지 않는다.

채점표의 내용: 기준 요구 목록(must 여부, 화면, 출처), 반드시 물었어야 할 질문, 당시 확정이 아니었던 항목, 실제 티켓과 PR 묶음, QA 결함과 그 원인.
