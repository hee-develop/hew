§0범위

§0.1다루는 것

설계 문서 §12 의 "1번 단계"다. 입력(PRD URL 또는 Jira 티켓 URL)에서 사람의 승인까지, 그리고 이 구간의 완료 기준을 재는 평가 장치다.

입력 → [0] 수집 → [1] 분석(테크니컬 매니저) → [1] QA 설계 → [1-1] 매니저 사수
     → 게이트(답변) → 답 반영 → [2] 티켓 메이커 → [2-1] 티켓 사수 → 게이트(승인) → 잠금
  • 수집, 원문 단위 열거
  • 요구사항 분석 문서, QA 시나리오, 티켓 분해안의 스키마와 결정적 검사
  • 매니저 사수, 티켓 사수의 작업 단위와 지적 형식
  • 게이트 페이지와 답·결정·승인의 저장 형식
  • 코어 명령 계약, 상태 기계, 에이전트 실행기
  • 리플레이, 결함 주입, 채점, 완료 기준
  • 실수 기록 형식

§0.2다루지 않는 것

Jira 쓰기 단계, 빌더, 빌더 사수, 코드 리뷰, QA 실행, PR 작성, 승인 뒤 요구 변경 처리, 종료 보고서. 다만 이 단계들이 읽을 산출물의 형식은 여기서 정한다.

§1.4에이전트 실행기

코어의 hew run 이 상태를 보고 다음 역할을 새 세션으로 띄운다.

claude -p "<패킷 경로를 읽고 수행하라는 고정 문장>" \
  --agent hew:<역할> --plugin-dir <hew> \
  --model <모델> --effort <effort> \
  --permission-mode dontAsk --allowedTools <역할별 목록> \
  --setting-sources project,local --strict-mcp-config --mcp-config '{"mcpServers":{}}' \
  --settings <실행용 설정(훅)> --output-format json < /dev/null
  • 수집 역할만 예외다. 연결된 커넥터(Atlassian, Figma)를 써야 하므로 --setting-sources·--strict-mcp-config 를 붙이지 않는다.
  • 그 밖의 역할은 사용자 설정의 훅·플러그인·MCP 없이 뜬다. 2026-11-14 실측에서 이렇게 띄운 세션은 사용자 훅이 0번 돌고 MCP 서버가 0개였으며 로그인은 그대로 됐다. 사실
  • 표준 입력을 닫지 않으면 세션이 입력을 3초 기다린다. 사실
  • --bare 는 쓰지 않는다. 구독 로그인을 읽지 않기 때문이다. 사실headless 문서 "bare mode doesn't use your subscription login"
  • 결과 JSON 에서 total_cost_usd, num_turns, session_id, 오류 여부를 costs.jsonl 에 남긴다.
  • 세션이 끝나면 코어가 상태를 다시 읽는다. 기대한 제출이 없으면 그 실행은 실패다. 같은 역할을 최대 2회 더 띄우고, 그래도 없으면 실행을 멈추고 사람에게 알린다(승인 전이므로 사람이 세션에 있다). 가정
  • 사용량 한도로 실패하면 리셋 시각까지 기다렸다 같은 역할을 다시 띄운다. 한도 실패를 어떻게 구분하는지는 미결실측.

  • 읽기·쓰기 범위는 실행용 설정의 훅(PreToolUse)이 지킨다. 읽기는 실행 폴더와 대상 저장소(사본) 안으로, 쓰기는 work/<실행 id>/ 안으로 제한한다. Bash 는 허용 명령만 받고, 명령에 든 경로가 범위 밖이면 거부한다. 2026-11-14 실측에서 Read 의 범위 밖 경로와 .. 경로가 거부됐다. 사실
  • Fable 5.2 를 medium 으로 쓸 때는 역할 정의에 "끝까지 진행" 문구를 넣는다(설계 §4.5).
  • 사수 세션의 고정 비용은 작다. 도구를 줄이고 사용자 설정 없이 띄운 Haiku 5.5 세션 한 번이 약 $0.001 이었다(도구 199개가 실린 기본 세션은 $0.006~0.010). 사실2026-11-14 그래도 작업 단위는 묶음으로 준다(§6.3).

§1.5제출과 검증

  • 에이전트는 초안을 work/ 에 쓰고 hew submit <종류> --file <경로> 를 부른다.
  • 코어는 스키마, 참조 무결성, 결정적 검사를 돌린다. 거부(종료 3)면 정본은 그대로이고 오류 목록을 돌려준다. 에이전트는 같은 세션에서 고쳐 다시 낸다.

§2.3근거 형식

근거는 항상 "원문 단위 id + 그 단위에서 그대로 옮긴 인용"이다.

  • 코어는 인용이 그 단위의 본문에 실제로 있는지 대조한다. 대조 전에 양쪽에서 공백·줄바꿈과 Markdown 강조 표시(**, __, 백틱)를 지운다.

§2.4revision

  • revision 은 승인 대상 전체의 해시다. 대상은 analysis(사람용·AI용 문장 모두), scenarios, plan, answers, 원천 manifest 다.
  • 계산: 키를 정렬한 JSON 의 sha256. 비용, 시각, 세션 id, 빈 값은 뺀다.
  • 승인은 revision 하나를 잠근다. 잠근 뒤 정본이 바뀌면 revision 이 달라지고 승인은 무효다.

§3원천과 원문 단위

§3.1수집

  • 수집 계획은 코어가 결정적으로 계산한다(hew source plan --run. 아무것도 바꾸지 않는다). run.json·sources/manifest.json·실패 기록(sources/failures.jsonl)에서 다음에 가져올 항목(id, what, tool_hint, register, note, skip)과 실패로 빠진 항목(failed), 막힌 일(blocked)을 낸다. 입력이 PRD URL 이면 PRD(페이지 id 는 URL 의 pageId= 또는 /pages/<id>/)를, 티켓 URL 이면 티켓을 첫 항목으로 두고, 등록된 본문에서 연결된 것(티켓의 상위 이슈 1단계, Figma 메타데이터, 캡처 대상 스크린샷, 같은 사이트의 관련 문서)이 계획에 새로 생긴다. 상한과 호스트·도구 허용 목록은 rules/collect.yaml 이 정한다.
  • hew init --repo 가 있으면 코어가 직접 git rev-parse <base 또는 HEAD> 로 SHA 를 얻어 code 원천을 등록한다(사례가 base 를 정했고 --base 가 없으면 사례의 값. git 이 실패하면 경고만 내고 등록하지 않는다). 계획에는 code 가 없을 때 "대상 저장소가 지정되지 않음" 이 막힌 일로 나온다.
  • hew init --case(replay) 는 사례 파일(§11.1 형식과 옛 형식 prd_version·known_at·blocked)을 읽어 run.json 의 case_info(story, known_at, prd_version, block.jira_keys·pr_numbers·heka_ids)에 싣고 known_at 은 run.known_at 에도 넣는다. 계획은 prd_version 이 있으면 그 버전만 가져오라고 적는다.
  • collector 가 계획대로 도구를 불러 가져온다. 도구 결과는 모델이 옮겨 적지 않는다. 수집 세션의 PostToolUse 훅(hooks/record.mjs)이 도구 결과를 원문 그대로 work/collector-<n>/calls/<번호>.payload 와 index.jsonl(번호, 도구, 입력, 크기, 해시, 큰 결과 여부)에 받아 적는다. 응답이 "결과가 커서 파일로 저장했다"는 안내문이면 그 파일의 내용을 받아 적는다. 사실2026-11-14 Claude Code 2.1.323 무인 세션에서 MCP 도구의 tool_response 는 문자열이고 큰 결과는 안내문으로 바뀐다
  • 등록: hew source calls 가 가장 최근 수집 작업 폴더의 호출 표(이미 등록됐는지 포함)를 보여 주고, hew source add … --from-call <번호> 가 그 payload 를 바이트 그대로 원천 파일로 복사한다(--file 과 둘 중 하나. 확장자는 JSON 으로 읽히면 .json, 아니면 .md. manifest 의 meta 에 call·tool·tool_use_id). Confluence 응답(content.nodes[0].body)과 Jira 응답(fields.description·fields.summary·renderedFields.description·최상위 description)은 원문 단위 추출이 그대로 받고, 제목·버전이 응답에 있으면 manifest 에서 비어 있을 때 채운다.
  • 실패: hew source fail --item <계획 항목 id> --reason 가 sources/failures.jsonl 에 덧붙인다. 같은 항목이 2회 실패하면 계획에서 빠지고 failed 에 실린다.
  • 완료: hew source done 은 필수 항목(입력에 따른 prd 또는 ticket, 그리고 code)이 없거나, PRD·티켓에 Figma 노드 링크가 있는데 figma_meta 가 하나도 없고 시도한 기록도 없거나, 계획에 아직 가져올 항목이 남아 있으면(skip·failed 제외) 종료 3 과 남은 항목 목록을 낸다. 필수가 아닌 항목의 2회 실패와 노드 지정 없는 Figma 링크의 건너뜀은 경고와 함께 통과시키고 run.json 의 collect_warnings 에 남긴다(manifest 에는 쓰지 않는다).
  • 수집 세션은 실행용 설정에 PreToolUse(hooks/guard.mjs 의 수집 프로필: HEW_GUARD_PROFILE=collector)와 PostToolUse(hooks/record.mjs, 매처 mcp__.*)를 함께 건다. 수집 프로필은 ToolSearch, rules/collect.yaml 의 mcp_allow 에 전체 일치하는 MCP 읽기 도구, 형식이 고정된 curl(curl -sS -L -o <쓰기 뿌리 안 경로> https://<허용 호스트>/…), hew source plan|calls|add|fail|done|list|request 를 추가로 허용한다. 사례의 차단 Jira 키(HEW_GUARD_BLOCK)가 MCP 입력에 단어 경계로 들어 있으면 거부하고, replay·shadow 에서는 executeRead 로 검색(jql·cql)을 하지 못하게 지정한 문서·버전 조회(getConfluenceContentVersion, listConfluenceContentVersions, getConfluencePage 류)만 허용한다.

  • 다음 회차에 다시 도는 단위 중 직전 회차에서 issue 였던 것의 inputs.previous 에 { claim, kind, response? } 를 싣는다. previous 는 단위의 hash 계산에서 뺀다. 사수는 답변을 읽고 지적이 풀렸는지 다시 판정하며, 답변이 근거를 들어 반박했고 그 근거가 맞으면 ok 를 낸다.

범위 안 변경 항목의 계산: 사람이 drop·hold 로 결정한 차이의 requirement_ids 에 든 요구는 요구 전체를 범위 밖으로 본다. 나머지 요구의 변경 항목이 범위 안이다. 티켓이 changes 없이 요구를 적으면 그 요구의 변경 전부를 맡은 것이다.

§7.2분해 규칙

rules/plan.yaml 에 두고 코드로 검사한다. 값은 heka 규칙에서 가져왔고 가정이다.

  • 티켓은 2~4SP 를 기본으로 한다. 넘으면 나눈다(heka prd-to-pr-pipeline-decisions-2026-09-r2).
  • 티켓 하나가 PR 하나일 필요는 없다. 함께 리뷰해야 뜻이 통하는 티켓은 한 PR 로 묶는다(2026-10-20 결정 6, APP-3008 실제 작업).
  • 피처플래그를 쓰는 일감은 에픽 브랜치를 만들지 않는다. 첫 PR 의 base 는 develop 이고 의존이 있으면 앞 PR 위에 쌓으며, 플래그 제거가 마지막 티켓이다(heka app-team-feature-flag-replaces-epic-branch).
  • PR 하나의 예상 변경 크기에 상한을 둔다. 값은 미결이다(이 저장소의 PR 크기 중앙값은 68줄이다).

§7.4티켓 사수

작업 단위는 티켓 하나다. 티켓 본문과 그 티켓이 덮는 요구(사람용 문장)를 주고 두 가지를 묻는다.

  • 티켓이 요구와 모순되거나 요구에 없는 일을 시키는가.
  • 티켓만 읽은 사람이 무엇을 해야 하는지 알 수 있는가(맥락 누락).

지적 형식과 반송(상한 2회)은 §6.4 와 같다. 반송은 티켓 메이커에게 간다. 작업 단위 코드는 T1(id T1:<티켓 id>), 지적 kind 는 ticket_contradicts·ticket_missing_change·ticket_missing_context, action 은 fix·ask 다. 묶음은 10개 이하로 나눈다. 답변(hew sasu respond --for plan)의 인용 대조는 그 지적 단위의 inputs 텍스트로 한다.

반송 상한(2회)을 채우고도 남은 차단 지적은 질문으로 바꾸지 않는다(분해안은 사람이 승인 단계에서 어차피 본다). doc/findings/plan-<회차>.json 의 그 지적에 to_gate: true 를 붙이고, 게이트의 승인 단계 "확인 필요" 에 "티켓 사수 지적(미해결): <claim> (대상 Tn)" 으로 싣는다. 분해안 정본의 verdict.reasons 에는 넣지 않는다.

§8.3두 번 보는 절차

  1. 답변: 사람이 질문에 답하고, 차이를 결정하고, 가정을 확인하고, 필요하면 모킹을 바꾼다.
  2. 사람이 "답 내보내기"로 받은 파일을 hew gate import --file 로 넣는다. 코어는 answers.json 에 합치고, 모두 채워졌으면 answers_complete 로 간다.
  3. 코어가 테크니컬 매니저와 QA 설계를 "답 반영" 패킷으로 다시 띄운다. 요구의 pending 이 confirmed 로 바뀌고, 범위 밖·보류가 정리된다. 바뀐 항목만 사수가 다시 본다.
  4. 답 반영에서 새 질문이 생기면 페이지를 다시 만들고 1로 돌아간다.
  5. 티켓 메이커와 티켓 사수가 돈다. 분해안이 실린 페이지를 같은 파일에 다시 만든다.
  6. 승인: 사람이 분해안을 확인한다. 수정 요청을 적으면 5로 돌아간다. 승인 버튼은 열린 항목이 없고 페이지의 revision 이 최신일 때만 켜진다.
  7. 승인 버튼을 누르면 승인이 든 파일이 내려온다. hew gate import 로 넣으면(또는 hew approve --revision 을 직접 부르면) 코어가 revision 이 현재 값과 같을 때만 잠근다.
  • 답의 시각이 이전 답보다 늦은 것만 새 답으로 본다.
  • 질문의 본문이 답한 뒤에 바뀌면 그 답은 "다시 답 필요"가 된다(답과 함께 질문 본문의 해시를 저장해 가린다).
  • 승인하면 게이트에서 내린 결정을 heka 결정 노트로 남긴다(live 모드만). 차이 결정과 차단 질문의 답은 건별로, 나머지는 묶어서 남긴다(heka hew-6-2026-10-23-mismatch 의 4). 아직 만들지 않았다. 미결

§8.4확인 요청서

mismatch_ratio 가 10%를 넘으면 PO·디자이너에게 보낼 확인 요청서 페이지를 함께 만든다. 대상(audience)이 po·designer 인 질문과 차이만 싣고, 선택지는 게이트와 같다(heka hew-review-request-page-decisions-2026-10-28). 요청서는 게이트를 대신하지 않는다. 다른 사람에게 보내는 문서라 게시가 필요하므로, 요청이 있을 때 만든다. 아직 만들지 않았다. 미결

§8.5여는 방법과 답 넣기

  • hew gate build --run <실행> 이 페이지를 만들고 경로를 gate/path.txt 에 적는다. --open 을 붙이면 브라우저로 연다.
  • 답은 hew gate import --run <실행> --file <내려받은 JSON> 으로 넣는다. 같은 파일을 다시 넣어도 결과가 같다(늦은 시각의 답만 반영).
  • hew run 은 사람 차례(gate_answering, gate_plan_review)에서 멈춘다. 답을 넣은 뒤 다시 부르면 이어 간다.
  • replay 모드는 사람이 답하지 않는다. 답안지에서 넣는다(§11.3).

§11.4채점표와 지표
