## 0. 한눈에 보기

PRD 하나(또는 작은 Jira 티켓 하나)를 넣으면 요구사항을 분석해 사람에게 한 번 확인받고, 그 뒤 티켓 생성·구현·리뷰·기기 QA 를 거쳐 draft PR 을 올리는 데까지 사람 없이 진행한다.

```
입력(PRD URL | Jira 티켓 URL)
  → [1]   테크니컬 매니저: 요구 분석 + 코드 수준 영향 분석
  → [1-1] 매니저 사수: 누락·환각 대조
  → [1]   QA 전문가(설계): 시나리오·모킹 초안
  → [G]   게이트(답변): 사람이 질문에 답하고 PRD–Figma 차이를 결정
  → [2]   티켓 메이커: 티켓 분해·PR 묶음안 → [2-1] 티켓 사수
  → [G]   게이트(승인): 사람이 분해안까지 확인하고 승인      ← 사람 개입은 이 게이트 한 곳
  → [W]   쓰기 단계: 승인된 티켓을 Jira 에 생성
  → 티켓마다   [3] 프로덕트 빌더 → [3-3] 빌더 사수 → [3-2] 코드 리뷰어      ← 서로 의존하지 않는 티켓은 동시에
  → PR 묶음마다 [4] QA 전문가(실행, iOS·Android) → [3-1] PR 작성자 → [W] draft PR      ← 임시 판단이 걸린 묶음은 QA 까지만
  → 종료 보고서: 임시 판단과 보류를 사람에게 보고
  → (사람) 임시 판단 재판단 → 그 묶음의 [3-1] PR 작성자 → [W] draft PR
  → (사람) ready 전환·리뷰어 지정
```

사람이 하는 일은 세 가지다. 게이트에서 답변·확인·승인, 종료 보고서의 임시 판단을 재판단(보류가 있으면 그 질문에 답), draft PR 을 ready 로 전환.

## 1. 주장과 요구

- 주장 [결정]: "요구사항이 잘 전달되었다면 이후 작업은 손을 대지 않아도 알아서 잘 만들어준다." 그래서 1번 단계가 이 워크플로우의 핵심이다.
- 운영 해석 [가정]: 요구가 **검증 가능한 형태**(인수 조건·검증 수단·QA 시나리오)로 확정되면 하류는 그 검증을 통과시키는 문제가 된다. 이 주장은 "승인 이후 사람 개입 횟수"와 "사후 결함의 원인 단계 분포"로 검증한다.
  - 근거 [사실]: 이전 구현의 과거 일감 대조에서 결함이 분석 단계에서 났다. 요구만으로 막지 못하는 결함도 있다.
- 요구 [결정]
  1. 성공 지표를 맞추기 위해 성능 우선으로 하되 가능한 한 비용을 최적화한다.
  2. 요구 확인·승인 이후는 완전 자동화한다. 단 세션 자체가 죽는 중단은 요구에서 제외한다.
  3. 각 단계의 산출물은 일관된 형태를 유지한다.
  4. 실수는 로그나 지식으로 기록하고 주기적으로 프롬프트·스킬·하니스를 고친다(개선 루프 자체는 추후 구축).
- 대상 일감 [결정]: PRD 가 있는 기능 개발과 작은 Jira 티켓. 입력이 PRD URL 이면 전체 경로, Jira 티켓 URL 이면 작은 티켓 경로다 [가정].
- 사용 범위 [결정]: 먼저 혼자 쓰고 나중에 팀으로 넓힌다. 개인 습관(PR 본문·커밋·주석 규칙)은 설정으로 분리한다.

## 3. 원칙

1. 사람 게이트는 요구 확인 1회다. [결정] 게이트 안에서 답변과 승인으로 두 번 보지만(§4.4) 승인은 한 번이고, 승인 뒤에는 사람을 기다리지 않는다.
2. 승인 이후 단계 진행은 프로그램(코어)이 정한다. [결정] 에이전트의 완료 선언은 상태를 바꾸지 않는다. 완료와 approve 는 코어가 직접 돌린 검사와 구조화된 지적에서 계산한 값이다. [가정]
3. 결정적으로 검사할 수 있는 것에 LLM 을 쓰지 않는다. [가정]
4. 검증자의 이름은 "사수"로 통일하고 작은 모델을 쓴다. [결정] 사수의 일은 좁고 검사 가능한 대조로 만들고, 그 모델이 실제로 잡는지 결함 주입으로 확인한다. [가정]
5. 산출물의 원본은 스키마로 검증되는 JSON 하나다. 사람용 페이지와 AI용 패킷은 그 원본에서 그린다. 단계마다 같은 틀(입력 revision, 항목, 근거, 미해결, 판정, 비용)을 쓴다. [가정]
6. 사람용 문장과 AI용 문장을 나눈다. [결정] AI용 문장에는 근거 인용, 코드 위치, 검증 방법, 적용 규칙만 담고 새 동작·조건은 담지 않는다. 승인 해시는 두 문장을 모두 포함한다. [가정]
7. 역할은 이름이 아니라 입력·출력·도구·권한으로 정의한다. [가정]
8. 모든 루프에 상한을 두고, 상한 도달은 통과가 아니라 보류다. [가정] 판단이 필요한 모호성은 보류하지 않고 임시 판단으로 진행한다(§6.1).
9. 실수 기록의 형식은 처음부터 남긴다. [가정]
10. heka 에 남은 규칙을 그대로 적용한다. [결정] 분석·게이트 규칙(출처 우선순위 Figma > PRD > ADR·티켓, 화면 우선 구성, 운영자(사내 어드민) 행 제외, PRD–시안 차이의 관점별 비교표, id 표기 `요구-n`·`화면-n`·`Q-n`·`D-n`·`A-n`)뿐 아니라 티켓·커밋·주석·PR 본문·리뷰·리플레이 규칙도 가져온다. 역할별 규칙 id 는 프로필에 둔다(§16, §17). heka 가 쓰인 내역은 세션마다 기록으로 남긴다(§16). [결정]
11. 티켓의 의존관계를 파악해 서로 의존하지 않는 티켓은 최대한 동시에 진행한다(§8.1). [결정]

### 4.1 빌더

- 입력은 요구 문서 조각(요구, 인수 조건, AI용 문장)과 티켓 둘 다다. [결정] 둘이 어긋나면 요구 문서가 우선한다. [결정] 어긋난 내용은 빌더가 기록하고, 실행이 끝날 때 쓰는 종료 보고서(§6.1)에 빠짐없이 싣는다. [결정] 티켓은 그 기록으로 고친다. [가정]
- effort 는 `medium` 으로 시작한다. [가정] `low` 는 기본값으로 쓰지 않는다. Sonnet 5.5 는 `low` 에서 끝내기 전에 멈춰 사용자에게 확인을 구하거나 실제 검사 없이 완료로 보고하는 일이 늘기 때문이다. [사실]
- 완료 판정은 빌더의 보고가 아니라 코어가 직접 돌린 검사(prettier, eslint, tsc, jest)다. 빌더 지시문에는 "실제 검사를 돌린 뒤 완료 보고"와 "끝까지 진행" 문구를 넣는다.
- 승급: 검사 실패가 반복되거나 리뷰에서 반송되면 `high`, 그래도 안 되면 상위 모델.
- 리뷰 반송으로 승급했을 때는 반송된 지적만 고치지 않고 티켓 작업을 다시 진행한다. [결정] 토큰을 줄이기 위해 기존 작업을 재사용한다. [결정]
  - 다시 진행하는 범위 [가정]: 승급된 빌더는 요구 문서 조각과 인수 조건을 기준으로 기존 diff 전체를 다시 본다. 리뷰 지적은 "어디가 약했는지"를 알리는 입력이고 작업 범위를 정하지 않는다. 지적된 곳만 고치면 리뷰어가 보지 못한 같은 종류의 문제가 남기 때문이다.
  - 재사용 방법 [가정]: 새 worktree 에서 처음부터 쓰지 않는다. 기존 worktree 와 커밋을 출발점으로 받아 맞는 부분은 그대로 두고 틀리거나 빠진 부분만 고친다. 패킷에는 기존 diff, 리뷰 지적, 직전 검사 결과를 싣는다.
  - 다시 진행한 뒤에는 코어 검사, 빌더 사수, 리뷰가 전체 diff 를 대상으로 다시 돈다. 리뷰-수정 라운드 한 번으로 센다(§4.2). [가정]
  - 검사 실패가 반복돼 승급한 경우는 리뷰 반송이 아니므로 실패한 검사를 고치는 데서 이어 간다. [가정]
- 대체물(임시 타입, 더미 에셋 등)을 쓴 자리에는 임시값임을 주석으로 적는다(§6.1). [결정]
- 건드린 화면의 조작 요소에는 testID 를 붙인다. [결정]
- 빌더를 분석 담당과 코드 담당으로 나누는 안은 채택하지 않았다. 티켓 한 장 크기의 일에서는 비용이 줄지 않기 때문이다. 큰 반복 작업에 한해 다시 볼 수 있다(§10 실험).

### 4.2 리뷰와 approve

- approve 는 에이전트의 판단이 아니라 "증거(실행 결과 또는 file:line 인용)가 있는 차단 지적 0건"을 코어가 계산한 값이다. [가정]
- 증거 없는 지적은 차단하지 않고 목록으로만 남긴다.
- 리뷰-수정 라운드는 상한을 둔다(값은 [미결], 출발점 3회). 반송으로 빌더가 승급하면 그 라운드는 지적만 고치는 것이 아니라 티켓 작업을 다시 진행하는 라운드다(§4.1).
- 리뷰 기준은 대상 저장소의 `REVIEW.md` 다(⛔️ 변경필요, ⚠️ 확인필요, 🟢 제안). PR 생성이 QA 뒤이므로 Copilot 리뷰는 PR 이 올라간 뒤에야 받는다. 내부 리뷰어가 같은 기준으로 먼저 걸러야 지표 3 을 지킬 수 있다.

### 4.3 외부 쓰기: 쓰기 전용 단계

- [결정] 쓰기 전용 단계를 따로 둔다. 조건은 "전달된 내용을 100% 그대로 실행한다는 보장"이고, 보장이 깨지면 에이전트가 직접 쓰는 방식으로 돌아간다.
- 배경: v0 은 "코어가 Jira REST·gh 로 쓴다"를 2026-10-20 결정에서 다시 따져 보지 않고 이어받았다. 사용자는 에이전트가 쓰는 것으로 생각했고 Jira 개인 API 토큰도 쓰지 않기로 했다(§14 의 26). 토큰 없이는 코어가 Jira REST 를 부를 수 없다.
- 보장의 근거: LLM 세션이 내용을 그대로 옮겨 적는다는 것은 보장할 수 없다. 그래서 내용을 세션에 맡기지 않는다. 쓰기 호출이 실행되기 직전에 코어의 훅(PreToolUse)이 도구 입력 전체를 검증된 내용으로 **교체**한다. 세션이 무엇을 적어 보내든 실행되는 입력은 코어가 정한 것이다.
- 구성 [가정]
  1. 내용은 에이전트(티켓 메이커, PR 작성자)가 파일로 내고 코어가 스키마·양식·매핑을 검증한다.
  2. 코어가 쓰기 한 건마다 의도를 먼저 기록한다(중복 방지용 고유 키 포함).
  3. Jira: 코어가 좁은 세션을 띄운다. 이 세션은 쓰기 도구를 허용 목록에 넣지 않고, 훅이 "허용 + 입력 교체"를 돌려줄 때만 호출이 실행된다. 훅이 돌지 않으면 호출은 승인받지 못해 거부된다. 훅은 의도 기록에 있는 건만, 한 번만 통과시킨다.
  4. 실행된 입력은 사후 훅(PostToolUse)이 기록하고, 코어가 검증된 내용과 같은지 대조한다. 이어서 Jira 를 다시 읽어 저장된 값을 확인한다. 세션의 보고 문장은 근거로 쓰지 않는다.
  5. PR: 모델을 거치지 않고 코어가 `gh` 로 올린다(본문 파일, `--attach`).
  6. 평가 모드에서는 쓰기 단계를 띄우지 않는다(§10 의 외부 쓰기 0).
- 실험 [사실, 2026-11-13, Claude Code 2.1.323, `claude -p`, Haiku 5.5, 로컬 임시 파일과 heka 검색만 사용]

| 실험 | 세션에 시킨 것 | 훅 | 결과 |
|---|---|---|---|
| 1 | 검증된 내용과 다른 명령 실행 | 다르면 거부 | 두 번 모두 거부, 아무것도 실행되지 않음 |
| 2 | 검증된 내용과 다른 명령 실행 | 입력 교체 | 실행된 입력이 검증된 내용과 일치 |
| 3 | MCP 도구(heka_search)를 다른 인자로 호출 | 입력 교체 | 실행된 입력이 검증된 내용과 일치. 세션은 자기가 보낸 인자로 실행된 줄 알고 보고함 |
| 4 | 검증된 내용을 읽고 그대로 호출 | 다르면 거부 | 통과, 일치 |

- 문서 근거 [사실]: PreToolUse 훅의 `updatedInput` 은 "Modifies the tool's input parameters before execution. Replaces the entire input object", 권한 규칙도 "against the input your hook returns, not the input Claude sent" 로 평가한다. MCP 도구도 같은 훅 대상이고, `claude -p` 는 `--bare` 가 아니면 훅을 싣는다([hooks](https://code.claude.com/docs/en/hooks), [headless](https://code.claude.com/docs/en/headless)).
- 보장의 범위
  - 보장하는 것: 실행되는 쓰기 호출의 입력이 검증된 내용과 같다. 다른 내용은 쓰이지 않는다.
  - 보장하지 않는 것: 쓰기가 반드시 일어난다는 것(세션이 호출하지 않으면 쓰기는 없고 코어가 다시 띄운다). 그리고 Jira 가 받은 입력을 저장하면서 바꾸는 부분(본문 서식 변환 등)인데, 이는 어느 방식이든 같고 다시 읽기로 확인한다.
  - 쓰기 직후 기록 전에 세션이 죽으면 쓰였는지 알 수 없다. 다시 쓰기 전에 고유 키로 조회해 중복을 막는다.
- Atlassian MCP(claude.ai 커넥터) [사실, 2026-11-14]: 무인 세션에서 `getJiraIssue` 를 `APP-1` 로 부르게 하고 훅이 `APP-3008` 로 바꿔 넣었더니 `APP-3008` 이 조회됐다. 읽기 호출에서는 입력 교체가 같게 동작한다. 쓰기 호출은 실제로 써 봐야 하므로 첫 실제 쓰기 때 저장된 값을 다시 읽어 확인한다.

### 4.4 티켓 분해와 PR 묶음: 게이트에서 승인

- [결정] 티켓을 몇 장으로 어떻게 나누는지, 어느 티켓을 한 PR 로 묶는지, 어떤 순서로 쌓는지는 게이트에서 사람이 승인한다(v0 의 "게이트에서 보지 않는다"를 뒤집음. 2026-10-20 결정 6 과 같은 방향).
- 시점 [가정]: 분해안은 질문이 모두 답해지고 차이가 결정된 뒤에 만든다. 답에 따라 요구가 바뀌면 분해를 다시 해야 하기 때문이다. 그래서 게이트는 같은 페이지에서 두 번 본다. 먼저 답변, 그다음 분해안 확인과 승인이다. 승인은 한 번이다.
- 게이트에 싣는 것 [가정]: 티켓 목록(제목, 덮는 요구, SP), PR 묶음, 의존 순서 그래프(heka `hew-gate-layout-decisions-2026-11-11`), base 브랜치와 피처플래그 사용 여부. 의존 순서 그래프는 승인 뒤 어떤 티켓이 동시에 진행되는지도 보여 준다(§8.1).
- 고치는 방법 [가정]: 사람은 분해안에 수정 요청을 적고, 티켓 메이커가 다시 만들어 같은 페이지에 재게시한다. 요구 자체는 이 단계에서 바뀌지 않는다.
- 승인 해시는 분해안을 포함한다. Jira 티켓은 승인 뒤 쓰기 단계가 만든다.
- 승인 뒤 요구 변경으로 생기는 추가 티켓(§6.2)은 다시 승인받지 않고 종료 보고서에 적는다. [가정]

### 4.5 설계 단계(테크니컬 매니저, QA 설계)의 모델

- [결정] 설계 단계에는 Fable 5.2 를 써도 된다. 단 effort 는 `medium` 이다. Opus 5.5 `high` 보다 성능이 좋을 때 적용한다.
- 현재 판정 [가정]: 공개된 측정만으로는 "더 좋다"가 확인되지 않는다. 그래서 출발점은 Opus 5.5 `high` 로 두고, 1번 단계 완료 기준을 재는 리플레이(§12)에서 같은 과거 PRD 를 두 구성으로 돌려 요구 재현율과 사후에 틀린 확정 항목 수가 나은 쪽을 쓴다.
- 공개 측정 [사실, Anthropic 내부 벤치마크, 2026-11-13 확인]

| 과제 | Fable 5.2 `medium` | Opus 5.5 `high` | 비고 |
|---|---|---|---|
| 저장소 코딩 과제 370개 | 88.9%, 시도당 $1.34 | 88.4%, 시도당 $1.38 | Fable 은 1회 실행 |
| 약 2,200만 토큰 코드에서 심어 둔 결함 찾기(F1) | 0.877, 실행당 $378 | 0.850, 실행당 $236 | 설정당 10회. 2.7점 높고 비용 1.6배 |
| 여러 자료를 읽고 종합하는 연구 과제 | 55.0%, 과제당 $2.16 | 미측정(`medium` 은 59.6%, $1.61) | Fable 은 출시 전 측정 |

- 낮은 effort 의 위험 [사실]: Fable 5.2 는 긴 다단계 작업에서 일이 끝나기 전에 턴을 마치는 일이 있고 `low`·`medium` 에서 더 잦다. "끝까지 진행" 문구를 넣으면 미완 종료가 절반쯤으로 줄고 출력 토큰은 약 30% 는다. 무인 실행이므로 Fable `medium` 을 쓸 때는 이 문구와 코어의 산출물 검증(스키마, 범위 장부 완결성)을 함께 둔다.
- 공식 권고 [사실]: "Start with Claude Opus 5.5 for most workloads. Use Claude Fable 5.2 for demanding reasoning and long-horizon agentic work, or when your evals on Claude Opus 5.5 at higher effort still fall short."
- 구독 요금제에서 두 모델의 한도 차이는 확인하지 못했다. [미결]

## 5. 요구사항 분석 문서(게이트)

### 5.1 구성

화면 우선으로 구성한다. 형식은 Artifact 페이지다. [가정]

1. 헤더: 일감, 원천 버전, 진행(질문 n개 중 m개 답변), 승인 버튼(모든 질문에 답해야 활성).
2. 화면 카드: 시안 이미지(AS-IS·TO-BE), 그 화면의 요구와 변경 목록, 인수 조건.
3. PRD–Figma 차이: 관점별 비교표와 결정(시안대로 / PRD 대로 / 구현 안 함 / 보류).
4. 질문: 추천안과 근거, "이 답이 바꾸는 구현". 추정 답으로 닫지 않는다.
5. 가정과 범위 밖: 범위 밖은 원문 인용이 있어야 한다.
6. 영향 분석 요약: 걸리는 코드 영역과 막힐 것(없는 에셋, 없는 API 필드 등). 막힐 것은 질문으로 올린다.
7. QA 시나리오와 모킹 표기. 모킹은 AI 가 정하고 사람은 여기서 바꾼다. [결정]
8. 티켓 분해와 PR 묶음. 질문이 모두 답해진 뒤 실리고, 사람이 확인해 승인한다(§4.4). [결정]

- 사람이 "모호한 곳만" 보면 실패는 모호하다고 표시되지 않은 오류에서 난다. 그래서 확정으로 표시된 항목도 화면별로 훑어볼 수 있게 싼 형태(이미지와 변경 목록)로 보인다.
- 작은 티켓은 같은 형식의 축소판을 쓴다. [가정]
- 차이가 많으면 PO·디자이너 확인 요청서를 함께 만든다. [가정, 2026-10-23·28 결정 계승]

### 5.2 사람용 문장과 AI용 문장

- 사람용: 짧은 변경 문장. 사람이 승인하는 대상이다.
- AI용: 그 변경의 근거 인용, 코드 위치, 검증 방법, 적용할 규칙. 새 동작이나 조건을 추가하지 못한다.
- 사수는 "AI용 문장에만 있는 동작"을 지적 대상으로 삼는다.
- 요구 문장은 검증 가능한 형식(예: WHEN … THE SYSTEM SHALL …)으로 쓴다. [제안]

### 5.3 매니저 사수의 일

| 일 | 수단 |
|---|---|
| 인용이 원문에 실제로 있는가, 범위 장부가 원문 전체를 덮는가 | 코드 |
| 요구가 인용한 근거로 뒷받침되는가(환각) | 작은 모델, 요구 단위 |
| 원문 단위(PRD 표의 행·문장, Figma 앱 화면)마다 덮는 요구가 있는가(누락) | 원문 단위 열거는 코드, 단위별 판정은 작은 모델 |
| "확정"으로 표시된 항목이 정말 확정인가 | 작은 모델 |

- 수정이 필요하면 테크니컬 매니저에게 되돌린다(상한 2회 [가정]). 남은 불일치는 게이트 질문으로 올린다.
- 작은 모델로 부족할 수 있는 곳 [미결]: 시안 이미지의 시각 차이(아이콘·컴포넌트 교체)와 어느 원문 단위에도 적혀 있지 않은 암묵 요구. 결함 주입에서 못 잡는 것으로 나오면 그 항목만 상위 모델로 올린다.

### 5.4 승인

- 승인은 문서의 해시(revision)를 잠근다. 사람용·AI용 문장, 시나리오, 티켓 분해와 PR 묶음을 모두 포함한다.
- 승인 뒤 문서가 바뀌면 revision 이 달라지고, 바뀐 부분에 대해서만 §6.2 의 규칙으로 처리한다.

## 6. 승인 이후 규칙

### 6.1 새 모호성

- 구현 중 모호성이 발견되면 멈추지 않는다. 에이전트가 스스로 판단해(**임시 판단**) 그 판단대로 작업을 끝까지 마치고, 종료 보고서로 사람에게 재판단을 요청한다. [결정, 2026-11-16. "해당 작업만 보류"(§14 의 8)를 바꿈] 의존하는 티켓의 후속 작업이 판단 보류 때문에 끊기지 않게 하기 위해서다.
- 물을 수 있는 것은 계획 단계(게이트)에서 미리 묻는다. [결정] 영향 분석에서 드러난 막힐 것(없는 에셋, 없는 API 필드 등)을 게이트 질문으로 올리는 것이 그 수단이다.
- 임시 판단의 기준 [가정]: 출처 우선순위(§3 의 10), 게이트에서 사람이 내린 비슷한 결정, 그래도 갈리면 나중에 뒤집기 쉬운 쪽.
- 임시 판단의 기록 [가정]: 질문, 고른 답과 근거, 고르지 않은 선택지, 그 판단에 걸린 티켓과 커밋. 뒤집혔을 때 고칠 범위를 알 수 있게 그 판단에서 나온 변경은 커밋을 나눈다.
- 실행 도중 생긴 임시 판단과 보류는 중간에 알리지 않는다. 나머지 작업이 모두 끝난 뒤 세션에 **종료 보고서**를 쓴다. [결정] 보고서에는 임시 판단 목록과 재판단 요청, 보류된 작업과 그 질문, 요구 문서와 티켓의 불일치(§4.1), 경험 우려(§7), 자동 반영한 요구 변경(§6.2)을 싣는다. [가정]
- 판단으로 풀 수 없는 막힘(받지 못한 에셋, 서버에 없는 API·필드, 권한)도 멈추지 않는다. 임시 타입이나 더미 에셋 같은 대체물로 그 티켓과 후속 티켓을 일단 진행한다. [결정, 2026-11-17] 대체물에 쓴 값은 가정이고, 임시값임을 코드의 그 자리에 주석으로 반드시 적는다. [결정]
  - 대체물도 임시 판단으로 기록한다. 무엇이 없어서 무엇으로 대신했는지와 파일 위치를 적는다. [가정]
  - 주석에는 찾을 수 있는 고정 표지를 쓴다. 대체물을 썼는데 표지가 없는 자리는 빌더 사수가 지적한다. [가정] 표지의 형식은 [미결]이다.
  - QA 보고서에는 대체물이 걸린 시나리오를 표시한다. [가정]
  - 실제 값이 오면 대체물을 걷어내는 작업을 띄운다. 표지가 남아 있는 묶음은 PR 을 올리지 않는다. [가정]
- 임시 판단이 걸린 PR 묶음은 구현·리뷰·QA 까지만 진행하고, PR 작성과 draft PR 은 사람이 재판단한 뒤에 한다. [결정, 2026-11-17] 임시 판단이 없는 묶음은 QA 를 통과하면 바로 draft PR 을 올린다(§14 의 9).
- 사람이 재판단한다. 그대로 두면 그 묶음은 PR 작성으로 넘어간다. 다르게 정하면 그 판단에 걸린 티켓과 그 티켓에 의존하는 티켓에 수정 작업을 띄우고, 검사·리뷰·QA 를 다시 거쳐 PR 을 올린다. [가정]
- 보류로 남는 경우 [가정]
  - 루프 상한 도달(§3 의 8). 판단할 질문이 아니라 검사·리뷰·QA 를 통과하지 못한 것이다. 그 티켓은 통과로 치지 않는다.
  - 대체물로도 진행할 수 없는 막힘.
  - 보류는 그 티켓에만 걸린다. 후속 티켓은 멈추지 않고, 보류된 티켓의 마지막 결과나 대체물 위에서 진행한다. 보류된 티켓이 든 묶음은 PR 을 올리지 않는다. 사람이 보고서의 질문에 답하면 보류된 작업을 다시 띄운다.
- 임시 판단 건수, 그중 뒤집힌 건수, 보류 건수는 1번 단계의 놓침으로 기록한다.

### 6.2 요구 변경

판정 단위는 티켓이고 기준은 단계다. [결정]

| 변경이 닿는 티켓의 상태 | 처리 |
|---|---|
| 시작 전 | 티켓과 요구 조각을 고친다 |
| 구현 중(제출 전) | 티켓을 고치고 빌더에게 변경분을 전달한다 |
| 제출됨(사수·리뷰·QA 중) 또는 완료 | 그대로 끝내고 변경분은 추가 티켓으로 만든다 |

- 감지: 단계 경계마다 PRD 버전과 Figma 를 다시 읽어 승인 시점과 비교한다. Slack·구두 변경은 사람이 접수한다. [가정]
- 뜻이 분명한 변경은 자동 반영하고 종료 보고서에 적는다. 모호하면 §6.1 대로 임시 판단으로 진행하고 재판단을 요청한다. [가정]
- 변경은 문서 revision, 시나리오, 티켓에 함께 반영한다.

### 6.3 중단

- 세션 자체가 죽는 중단(크래시, 재부팅)은 요구에서 제외한다. [결정] 다만 상태는 파일에 남겨서 사람이 다시 띄우면 이어서 간다. [가정]
- 사용량 한도에 걸리면 프로그램이 리셋 시각까지 기다렸다 같은 단계를 다시 띄운다. [가정]

## 7. QA

- 목적 [결정]: **인간 사용자의 경험에 문제 되는 부분을 없애는 것**이다. 과거 결함 유형 목록은 그 목적을 위한 수단이다.
- 판정은 두 층이다.
  1. 기능: 승인된 시나리오의 통과 여부.
  2. 경험 점검: 시나리오의 각 화면과 전환을 사람 관점의 점검표로 본다. 점검표는 과거 QA 결함에서 뽑는다(예: 잘림, 겹침, 눌리지 않음, 빈 화면, 오류 문구 없음, 뒤로 가기 이상, 키보드 가림). 근거는 스크린샷이나 녹화다.
- 처리 [결정]
  - 명백한 결함(깨짐, 잘림, 겹침, 먹통, 크래시)은 빌더가 고치고 다시 검증한다. 통과할 때까지 반복하되 상한과 환경 실패/결함 분류를 둔다.
  - 시안·요구대로지만 불편해 보이는 것("경험 우려")은 고치지 않고 QA 보고서와 PR 본문에 근거 화면과 함께 남긴다.
- 시나리오 [결정]
  - 설계는 승인 전, 실행은 구현 후.
  - 기대 결과는 잠근다. QA 가 고칠 수 있는 것은 절차(셀렉터, 대기)뿐이다.
  - 에이전트 탐색은 처음 한 번만 하고, 통과한 경로는 결정적 스크립트로 고정해 재실행한다.
- 모킹 [결정]: OpenAPI 에서 만든 mock 을 쓰고 시나리오마다 실서버/모킹을 표기한다. 모킹으로만 통과한 시나리오는 보고서에 "통합 미검증"으로 남긴다.
- 기기 [결정]: 처음부터 iOS 시뮬레이터와 Android 에뮬레이터 둘 다 통과해야 PR 을 올린다.
- 테스트 계정 [결정]: 사용자가 준 테스트 계정으로 워크플로우가 직접 로그인한다. 계정이 여러 개 필요하면(역할·구매 이력이 다른 상태 등) QA 설계 단계가 필요한 상태를 적어 게이트에서 요청한다. 계정 정보는 저장소 밖 파일에 두고 문서·heka·로그에 비밀번호를 남기지 않는다. [가정, 2026-10-20 결정 8 계승]
- 서버 [결정]: 일감마다 쓰는 서버가 다르므로 워크플로우가 직접 고른다. 변경된 API 가 반영돼 있는 환경을 찾는 것이 기준이다. 방법 [가정]: 영향 분석에서 뽑은 변경 API 경로·필드를 환경별 `openapi.json`(staging, dev-N)과 대조해 모두 있는 환경을 고르고, 고른 환경과 근거를 게이트 문서와 QA 보고서에 적는다. 어느 환경에도 없으면 해당 시나리오는 모킹으로 표기한다.
- 산출물: 시나리오별 스크린샷, 사람에게 가는 QA 보고서, PR 에 붙는 AS-IS·TO-BE.
- PR 스크린샷 [결정: 과거 PR 을 따른다]
  - 형식 [사실]: 본문의 `## 스크린샷` 절에 화면 묶음별 소제목을 두고, 상태 이름을 머리글로 한 HTML 표에 `<img src="…" width=300 />` 로 넣는다(PR #1749 등, heka `pr-300px-img-width-300`).
  - 올리는 방법 [사실]: `gh pr create|edit --attach` 로 올린다(gh 2.99.0 이상, 이 머신은 2.103.3). 치환은 마크다운 이미지 참조에만 되므로 ① 마크다운 참조로 올려 asset URL 을 받고 ② 본문을 HTML 표로 다시 써서 저장하는 두 단계다(heka `github-image-upload-no-documented-api-gh-attach-2026-10`). 올린 asset 은 지울 수 없다.
- 도구 후보 [사실]: Maestro 2.12.1 은 MCP 를 내장한다(화면 계층 조회, 스크린샷, YAML 실행). agent-device 는 탐색 세션을 기록해 호환 흐름을 Maestro YAML 로 내보낸다. Maestro 의 AI 단언은 실험 기능이고 화면이 Maestro Cloud 로 나가므로 게이트로 쓰지 않는다. Maestro 에는 네트워크 모킹이 없다.
- 알려진 어려움 [사실]: 대상 앱에 testID 와 E2E 자산이 거의 없다. 과거 Maestro 시도는 딥링크 이동을 한 번도 확인하지 못했다. 모달·바텀시트·에러·빈 상태는 딥링크로 도달하지 못한다. 에이전트의 QA 판단은 보정 없이는 관대하다.

## 8. 진행 프로그램(코어)

- 프로그램이 상태 파일을 보고 다음 단계의 에이전트를 새 세션(`claude -p`)으로 띄운다. [결정] 세션 하나는 한 단계의 일 하나만 맡고, 승인 뒤 티켓 단계에서는 여러 세션이 동시에 돈다(§8.1). 구독 로그인을 쓴다. [가정]
- 에이전트는 자기 단계의 패킷만 받는다. 산출물은 파일로 내고, 코어가 스키마와 참조 무결성을 검증한 뒤에만 상태가 바뀐다.
- 단계별 비용은 실행 결과의 `total_cost_usd` 로 집계한다.
- `claude -p` 는 권한 모드를 정하지 않으면 Manual 로 시작한다. 허용 규칙을 명시해야 한다. [사실]
- 승인 전 단계(분석, 게이트 게시, 답 반영)를 어떤 세션에서 돌릴지는 [미결]이다. 무인 세션에서 Artifact 게시와 답 읽기가 되는지 실측해야 한다.

### 8.1 티켓의 의존관계와 동시 진행

- 티켓의 의존관계를 파악해 서로 의존하지 않는 티켓은 최대한 동시에 진행한다. [결정, 2026-11-16]
- 의존관계의 출처: 분해안의 티켓별 선행 티켓(`depends_on`)과 PR 묶음의 순서·base 다. 게이트에서 사람이 승인한 값이고(§4.4), 순환과 순서 모순은 승인 전에 코드로 검사한다.
- 진행 규칙 [가정]
  - 선행 티켓이 모두 리뷰까지 통과한 티켓을 "준비됨"으로 보고, 준비된 티켓은 기다리지 않고 동시에 띄운다. 티켓마다 전용 worktree 를 쓴다.
  - 선행 티켓이 있는 티켓은 그 티켓의 결과 위에서 시작한다.
  - 선행 티켓에 임시 판단이나 대체물이 걸려 있어도, 선행 티켓이 보류돼도 후속 티켓은 진행한다(§6.1).
  - QA 와 PR 작성은 묶음 단위다. 한 묶음의 티켓이 모두 끝나면 다른 묶음이 진행 중이어도 시작한다. 임시 판단이 걸린 묶음은 QA 까지만 하고 재판단을 기다린다(§6.1).
- 같은 파일을 고칠 것으로 예상되는 티켓들도 의존이 없으면 동시에 진행하고, 충돌은 합칠 때 해소한다. [결정, 2026-11-17]
  - 합치는 순서 [가정]: 묶음 안의 티켓은 분해안의 순서대로 합친다.
  - 충돌 해소 [가정]: 충돌이 나면 뒤에 합치는 티켓의 빌더를 다시 띄워 해소한다. 충돌 해소는 검증되지 않은 변경을 만들므로, 해소한 결과는 코어 검사·빌더 사수·리뷰를 다시 거친다.
- [미결] 동시에 띄울 세션 수의 상한(구독 사용량 한도와 로컬 자원), 티켓의 변경을 합치는 시점(티켓이 끝날 때마다인지 묶음이 모두 끝난 뒤인지), 기기 QA 를 묶음끼리 동시에 돌릴 수 있는지(시뮬레이터·에뮬레이터 수).

## 10. 평가와 점진적 개선

"같은 일감은 반복할 수 없다"는 제약은 평가 장치로 푼다. [결정: 동의]

- 리플레이: 과거 일감을 당시 base SHA, PRD 버전, 지식 시점으로 복원해 여러 번 다시 돌린다.
- 결함 주입
  - 매니저 사수: 요구 하나를 지우거나 바꾼 문서를 주고 잡는지 본다.
  - 코드 리뷰어: 인수 조건 위반을 심고 잡는지, 정상 코드를 결함으로 오판하지 않는지 본다.
  - QA: 앱에 알려진 버그를 심고 시나리오가 잡는지 본다.
- 병행 실행: 사람이 실제 업무를 하는 동안 외부 쓰기 없이 같이 돌려 비교한다.
- 외부 쓰기 0 [결정]: 리플레이·결함 주입·병행 실행에서는 Confluence·Jira·GitHub 에 실제 결과물을 올리지 않는다(이미 있는 결과물과 중복되기 때문이다). 티켓은 파일로, PR 은 로컬 브랜치와 본문 파일로만 남긴다. 평가 모드에서는 쓰기 단계 자체를 띄우지 않아 구조로 막는다. [가정]
- 컨텍스트 차단 [결정]: 이미 작업된 PRD 를 다시 돌릴 때는 그 일감의 기존 작업을 모르는 상태로 진행한다(편향 방지). 차단 대상 [가정]
  - 코드: 저장소를 당시 base SHA 로 복원하고 이력을 단일 커밋으로 다시 만든다. base 는 PR 의 `base.sha` 가 아니라 first-parent 이력에서 직접 계산한다(heka `github-pr-base-sha-not-creation-time-r2`).
  - 문서: PRD 는 당시 버전을 읽는다(heka `confluence-version-history-via-atlassian-mcp-prd-d9-r3`). 그 일감의 [MO] 하위 작업, PR, QA 티켓은 읽지 못하게 한다.
  - 지식: heka 는 당시 시점(`known_at`)까지만 보이게 하고, 그 일감에서 나온 노트(게이트 결정, 대조 기록)는 뺀다. 세션에 자동으로 붙는 heka 주입 훅도 같은 시점으로 고정하거나 끈다. [미결: 방법 실측]
  - 기록: 과거 세션 원문(recall)과 메모리는 읽지 못하게 한다. 실행 에이전트는 모두 새 세션으로 띄운다.
  - 채점표(gold)는 에이전트가 볼 수 없는 곳에 두고, 사람이 에이전트 산출물을 보기 전에 교정한다(heka `hew-slice1-decisions-2026-10-20`).
  - 한계 [미결]: Figma 는 과거 버전을 읽는 수단을 확인하지 못했다. 현재 시안을 읽으면 그 뒤의 수정이 섞인다.
- 프롬프트를 고치며 들여다본 케이스와 채점에만 쓰는 케이스를 나눈다. [제안] APP-3008·APP-2513 은 실패 내용이 이미 설계와 heka 규칙에 반영돼 있어, 이 둘의 점수만으로는 새 일감에서도 통하는지 알 수 없다.
- 회귀 케이스는 실제 실패에서 뽑는다. 이미 가진 실패(시안 instance 교체 누락, 추정으로 닫은 범위, 운영자 행 인용)가 첫 케이스다.
- 비결정적이므로 케이스마다 여러 번 돌리고, LLM 채점기는 사람 판정과 맞춘다.
- 좁은 행동 회귀는 `claude plugin eval` 로(케이스당 기본 3회, 플러그인 없는 기준선 비교, MCP mock). 요구 재현율처럼 계산이 필요한 채점은 자체 러너로.
- 평가로 정할 실험
  1. 사수의 모델 등급(Haiku 5.5 로 충분한가, 시안 시각 대조 포함).
  2. 빌더 effort: `medium` 대 `low`.
  3. 빌더 단일 대 분석·코드 분리(큰 반복 작업에 한해).
  4. 설계 단계(테크니컬 매니저, QA 설계): Opus 5.5 `high` 대 Fable 5.2 `medium`(§4.5).
- 실수 기록 형식(처음부터 남긴다): 발견 단계, 원인 단계, 유형, 근거, 당시 프롬프트·에이전트 정의 버전(git SHA), 실행 id.
- 프롬프트를 고치는 규칙 [가정]
  - 규칙을 하나 넣을 때 그 규칙을 낳은 실패를 회귀 케이스로 같이 넣는다.
  - 고치는 순서는 코드 검사 > 스키마·패킷 > 절차 > 프롬프트 문장이다.
  - 주기적으로 규칙을 빼 보고 점수가 안 떨어지면 지운다.

## 16. 적용하는 heka 규칙

역할별 규칙 id 는 프로필의 `heka` 에 둔다(§17). [결정] 각 단계의 패킷에는 그 단계의 규칙 id 만 싣고, 에이전트는 본문을 `heka_expand` 로 읽는다. 사람이 말한 것이 아니라 AI 가 뽑아 검수되지 않은 노트는 적용 전에 본문을 확인한다.

### 16.1 heka 사용 기록

- heka 플러그인이 설치된 Claude Code 는 모든 세션에서 heka 가 쓰일 때 기록을 남긴다. [결정, 2026-11-16] 목적은 두 가지다. 그 세션이 지켜야 했던 규칙이 무엇이었는지 파악하는 것, 그리고 어떤 맥락에서 어떻게 쓰였는지 확인해 뒤의 판단을 개선하는 것이다.
- 기록을 남기는 주체는 heka 플러그인이다. [가정] 이 워크플로우에만 있는 기능이 아니라 사람이 직접 쓰는 세션에도 똑같이 적용된다. 워크플로우가 띄우는 무인 세션(`claude -p`)도 플러그인을 싣고 돌므로 같은 기록이 남는다.
- 기록 한 건에 담는 것 [가정]: 시각, 세션, 쓰인 방식(검색, 본문 읽기, 훅의 자동 주입, 등록), 대상 노트 id, 호출한 맥락(질의나 그때의 도구 호출).
- 이 워크플로우가 하는 일 [가정]: 세션을 띄울 때 실행 id 와 단계를 넘겨 기록이 실행과 이어지게 하고, 실행이 끝나면 패킷에 실린 규칙 id 와 대조한다. 패킷에 실렸는데 읽히지 않은 규칙, 읽혔는데 지켜지지 않은 규칙을 실수 기록(§10)의 근거로 쓴다.
- 평가 실행의 컨텍스트 차단(§10)과 부딪치지 않게, 기록은 쓰기만 하고 실행 에이전트에게 보여 주지 않는다. [가정]

## 17. 프로필: 도메인·팀에 특화된 값은 저장소 밖에 둔다

[결정] 특정 서비스·팀에 묶인 값(주체 낱말, 티켓 제목 형식, SP 범위, PR 상한, 역할별 heka id, 외부 서비스 주소, 도메인 설명)은 저장소가 아니라 프로필 폴더에 둔다. 저장소는 가상의 서비스로 채운 예시(`profiles/example`)만 가진다.

- 위치를 정하는 순서: 환경 변수 `HEW_PROFILE_DIR` → `~/.hew/profile`(폴더가 있을 때) → 저장소의 `profiles/example`(끝 기본값).
- 파일 두 개: `profile.yaml`(필수), `domain.md`(선택. 없거나 비면 해당 패킷 절을 뺀다).
- `profile.yaml` 키: `actors`(주체별 판정 낱말, 정규식 조각, 대소문자 무시), `plan`(`sp`, `title.format`, `pr.max_tickets`·`pr.base`, 선택 `notes`), `heka`(역할별 규칙 노트 id), `connections.atlassian_cloud_id`. 알 수 없는 키와 틀린 값은 어느 파일의 어느 키인지 알리고 내부 오류로 멈춘다.
- 패킷: `domain.md` 는 `## 도메인 안내` 절로 그대로 실린다(`## 따를 규칙` 앞). 역할 정의가 이 절을 가리키는 테크니컬 매니저와 QA 설계의 패킷에만 싣는다. 사수 패킷에 실으면 결함 주입 평가에서 포착이 떨어졌다(같은 결함 하나를 반복해 쟀을 때 실으면 4번 중 0번, 싣지 않으면 10번 중 7번. 표본이 작아 다시 잴 필요가 있다). ticket-maker·ticket-sasu 패킷에는 `## 팀 규칙` 절(제목 형식, SP 범위, PR 상한, base, `notes`)이 실린다.
- 저장소의 `rules/` 에 남는 것: 역할의 모델·도구·참고 파일(`roles.yaml`), 수집 한도와 허용 도구(`collect.yaml`), 티켓 본문 금지 규칙(`plan.yaml` 의 `body_forbidden`).
- 가드 훅의 "수집 프로필"(`HEW_GUARD_PROFILE`)은 이것과 다른 것이다. 훅이 어떤 도구를 허용할지 정하는 모드일 뿐 프로필 폴더와 무관하다.
- 테스트는 환경 변수로 `profiles/example` 을 고정해 개발자 홈의 실제 프로필이 섞이지 않게 한다.
