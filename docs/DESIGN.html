§0한눈에 보기

PRD 하나(또는 작은 Jira 티켓 하나)를 넣으면 요구사항을 분석해 사람에게 한 번 확인받고, 그 뒤 티켓 생성·구현·리뷰·기기 QA 를 거쳐 draft PR 을 올리는 데까지 사람 없이 진행한다.

입력(PRD URL | Jira 티켓 URL)
  → [1]   테크니컬 매니저: 요구 분석 + 코드 수준 영향 분석
  → [1-1] 매니저 사수: 누락·환각 대조
  → [1]   QA 전문가(설계): 시나리오·모킹 초안
  → [G]   게이트(답변): 사람이 질문에 답하고 PRD–Figma 차이를 결정
  → [2]   티켓 메이커: 티켓 분해·PR 묶음안 → [2-1] 티켓 사수
  → [G]   게이트(승인): 사람이 분해안까지 확인하고 승인      ← 사람 개입은 이 게이트 한 곳
  → [W]   쓰기 단계: 승인된 티켓을 Jira 에 생성
  → 티켓마다   [3] 프로덕트 빌더 → [3-3] 빌더 사수 → [3-2] 코드 리뷰어
  → PR 묶음마다 [4] QA 전문가(실행, iOS·Android) → [3-1] PR 작성자 → [W] draft PR
  → (사람) ready 전환·리뷰어 지정

사람이 하는 일은 세 가지다. 게이트에서 답변·확인·승인, 종료 보고서의 보류 질문에 답, draft PR 을 ready 로 전환.

§1주장과 요구

  • 주장 결정: "요구사항이 잘 전달되었다면 이후 작업은 손을 대지 않아도 알아서 잘 만들어준다." 그래서 1번 단계가 이 워크플로우의 핵심이다.
  • 운영 해석 가정: 요구가 검증 가능한 형태(인수 조건·검증 수단·QA 시나리오)로 확정되면 하류는 그 검증을 통과시키는 문제가 된다. 이 주장은 "승인 이후 사람 개입 횟수"와 "사후 결함의 원인 단계 분포"로 검증한다.
    • 근거 사실: 이전 구현의 과거 일감 대조에서 결함이 분석 단계에서 났다. 요구만으로 막지 못하는 결함도 있다.
  • 요구 결정
    1. 성공 지표를 맞추기 위해 성능 우선으로 하되 가능한 한 비용을 최적화한다.
    2. 요구 확인·승인 이후는 완전 자동화한다. 단 세션 자체가 죽는 중단은 요구에서 제외한다.
    3. 각 단계의 산출물은 일관된 형태를 유지한다.
    4. 실수는 로그나 지식으로 기록하고 주기적으로 프롬프트·스킬·하니스를 고친다(개선 루프 자체는 추후 구축).
  • 대상 일감 결정: PRD 가 있는 기능 개발과 작은 Jira 티켓. 입력이 PRD URL 이면 전체 경로, Jira 티켓 URL 이면 작은 티켓 경로다 가정.
  • 사용 범위 결정: 먼저 혼자 쓰고 나중에 팀으로 넓힌다. 개인 습관(PR 본문·커밋·주석 규칙)은 설정으로 분리한다.

§2성공 지표

#지표 결정집계 규칙기준선 사실
1PRD 요구 누락 0건(작업 중 바뀐 요구 포함)사후에 리뷰·QA·PO 지적 중 "요구 누락"으로 분류된 건수 + 리플레이의 요구 재현율. 판정 기준은 승인된 문서와 승인 뒤 접수된 변경 가정없음(리플레이로 측정)

3PR 에 p4 이상 댓글 0건사람이 p1~p4 를 붙인 댓글 + Copilot 의 변경필요(⛔️)·확인필요(⚠️) 댓글 + 리뷰 뒤 코드 수정 커밋이 생겼는지 결정—
  • 지표 2·3 은 사람이 작업한 결과도 이미 0 근처다. 지켜야 할 하한선으로 쓰고, 개선됐는지는 리플레이와 아래 보조 지표로 본다.
  • 보조 지표 가정
    • 승인 이후 사람 개입 횟수(보류 질문 수). 주장과 요구 2 의 직접 지표다.
    • 사후에 틀린 것으로 드러난 "확정" 항목 수, 지어낸 요구 수, 질문 수율(문서에 이미 답이 있던 질문의 비율).
    • 게이트 체류 시간(문서 게시부터 승인까지).
    • 수락된 변경당 비용, 단계별 비용.
    • 단계별 결함 봉쇄(결함이 어느 단계에서 잡혔는가).
  • 누락만 재면 요구를 부풀리거나 질문을 쏟아내는 쪽으로 쏠린다. 그래서 지표 1 은 정밀도·질문 수율과 같이 본다.

§3원칙

  1. 사람 게이트는 요구 확인 1회다. 결정 게이트 안에서 답변과 승인으로 두 번 보지만(§4.4) 승인은 한 번이고, 승인 뒤에는 사람을 기다리지 않는다.
  2. 승인 이후 단계 진행은 프로그램(코어)이 정한다. 결정 에이전트의 완료 선언은 상태를 바꾸지 않는다. 완료와 approve 는 코어가 직접 돌린 검사와 구조화된 지적에서 계산한 값이다. 가정
  3. 결정적으로 검사할 수 있는 것에 LLM 을 쓰지 않는다. 가정
  4. 검증자의 이름은 "사수"로 통일하고 작은 모델을 쓴다. 결정 사수의 일은 좁고 검사 가능한 대조로 만들고, 그 모델이 실제로 잡는지 결함 주입으로 확인한다. 가정
  5. 산출물의 원본은 스키마로 검증되는 JSON 하나다. 사람용 페이지와 AI용 패킷은 그 원본에서 그린다. 단계마다 같은 틀(입력 revision, 항목, 근거, 미해결, 판정, 비용)을 쓴다. 가정
  6. 사람용 문장과 AI용 문장을 나눈다. 결정 AI용 문장에는 근거 인용, 코드 위치, 검증 방법, 적용 규칙만 담고 새 동작·조건은 담지 않는다. 승인 해시는 두 문장을 모두 포함한다. 가정
  7. 역할은 이름이 아니라 입력·출력·도구·권한으로 정의한다. 가정
  8. 모든 루프에 상한을 두고, 상한 도달은 통과가 아니라 보류다. 가정
  9. 실수 기록의 형식은 처음부터 남긴다. 가정
  10. heka 에 남은 규칙을 그대로 적용한다. 결정 분석·게이트 규칙(출처 우선순위 Figma > PRD > ADR·티켓, 화면 우선 구성, 운영자(사내 어드민) 행 제외, PRD–시안 차이의 관점별 비교표, id 표기 요구-n·화면-n·Q-n·D-n·A-n)뿐 아니라 티켓·커밋·주석·PR 본문·리뷰·리플레이 규칙도 가져온다. 역할별 규칙 id 는 프로필에 둔다(§16, §17).

§4.1빌더

  • 입력은 요구 문서 조각(요구, 인수 조건, AI용 문장)과 티켓 둘 다다. 결정 둘이 어긋나면 요구 문서가 우선한다. 결정 어긋난 내용은 빌더가 기록하고, 실행이 끝날 때 쓰는 종료 보고서(§6.1)에 빠짐없이 싣는다. 결정 티켓은 그 기록으로 고친다. 가정
  • effort 는 medium 으로 시작한다. 가정 low 는 기본값으로 쓰지 않는다. Sonnet 5.5 는 low 에서 끝내기 전에 멈춰 사용자에게 확인을 구하거나 실제 검사 없이 완료로 보고하는 일이 늘기 때문이다. 사실
  • 완료 판정은 빌더의 보고가 아니라 코어가 직접 돌린 검사(prettier, eslint, tsc, jest)다. 빌더 지시문에는 "실제 검사를 돌린 뒤 완료 보고"와 "끝까지 진행" 문구를 넣는다.
  • 승급: 검사 실패가 반복되거나 리뷰에서 반송되면 high, 그래도 안 되면 상위 모델.
  • 건드린 화면의 조작 요소에는 testID 를 붙인다. 결정
  • 빌더를 분석 담당과 코드 담당으로 나누는 안은 채택하지 않았다. 티켓 한 장 크기의 일에서는 비용이 줄지 않기 때문이다. 큰 반복 작업에 한해 다시 볼 수 있다(§10 실험).

§4.2리뷰와 approve

  • approve 는 에이전트의 판단이 아니라 "증거(실행 결과 또는 file:line 인용)가 있는 차단 지적 0건"을 코어가 계산한 값이다. 가정
  • 증거 없는 지적은 차단하지 않고 목록으로만 남긴다.
  • 리뷰-수정 라운드는 상한을 둔다(값은 미결, 출발점 3회).
  • 리뷰 기준은 대상 저장소의 REVIEW.md 다(⛔️ 변경필요, ⚠️ 확인필요, 🟢 제안). PR 생성이 QA 뒤이므로 Copilot 리뷰는 PR 이 올라간 뒤에야 받는다. 내부 리뷰어가 같은 기준으로 먼저 걸러야 지표 3 을 지킬 수 있다.

§4.3외부 쓰기: 쓰기 전용 단계

  • 결정 쓰기 전용 단계를 따로 둔다. 조건은 "전달된 내용을 100% 그대로 실행한다는 보장"이고, 보장이 깨지면 에이전트가 직접 쓰는 방식으로 돌아간다.
  • 배경: v0 은 "코어가 Jira REST·gh 로 쓴다"를 2026-10-20 결정에서 다시 따져 보지 않고 이어받았다. 사용자는 에이전트가 쓰는 것으로 생각했고 Jira 개인 API 토큰도 쓰지 않기로 했다(§14 의 26). 토큰 없이는 코어가 Jira REST 를 부를 수 없다.
  • 보장의 근거: LLM 세션이 내용을 그대로 옮겨 적는다는 것은 보장할 수 없다. 그래서 내용을 세션에 맡기지 않는다. 쓰기 호출이 실행되기 직전에 코어의 훅(PreToolUse)이 도구 입력 전체를 검증된 내용으로 교체한다. 세션이 무엇을 적어 보내든 실행되는 입력은 코어가 정한 것이다.
  • 구성 가정
    1. 내용은 에이전트(티켓 메이커, PR 작성자)가 파일로 내고 코어가 스키마·양식·매핑을 검증한다.
    2. 코어가 쓰기 한 건마다 의도를 먼저 기록한다(중복 방지용 고유 키 포함).
    3. Jira: 코어가 좁은 세션을 띄운다. 이 세션은 쓰기 도구를 허용 목록에 넣지 않고, 훅이 "허용 + 입력 교체"를 돌려줄 때만 호출이 실행된다. 훅이 돌지 않으면 호출은 승인받지 못해 거부된다. 훅은 의도 기록에 있는 건만, 한 번만 통과시킨다.
    4. 실행된 입력은 사후 훅(PostToolUse)이 기록하고, 코어가 검증된 내용과 같은지 대조한다. 이어서 Jira 를 다시 읽어 저장된 값을 확인한다. 세션의 보고 문장은 근거로 쓰지 않는다.
    5. PR: 모델을 거치지 않고 코어가 gh 로 올린다(본문 파일, --attach).
    6. 평가 모드에서는 쓰기 단계를 띄우지 않는다(§10 의 외부 쓰기 0).

§4.4티켓 분해와 PR 묶음: 게이트에서 승인

  • 결정 티켓을 몇 장으로 어떻게 나누는지, 어느 티켓을 한 PR 로 묶는지, 어떤 순서로 쌓는지는 게이트에서 사람이 승인한다(v0 의 "게이트에서 보지 않는다"를 뒤집음. 2026-10-20 결정 6 과 같은 방향).
  • 시점 가정: 분해안은 질문이 모두 답해지고 차이가 결정된 뒤에 만든다. 답에 따라 요구가 바뀌면 분해를 다시 해야 하기 때문이다. 그래서 게이트는 같은 페이지에서 두 번 본다. 먼저 답변, 그다음 분해안 확인과 승인이다. 승인은 한 번이다.
  • 게이트에 싣는 것 가정: 티켓 목록(제목, 덮는 요구, SP), PR 묶음, 의존 순서 그래프(heka hew-gate-layout-decisions-2026-11-11), base 브랜치와 피처플래그 사용 여부.
  • 고치는 방법 가정: 사람은 분해안에 수정 요청을 적고, 티켓 메이커가 다시 만들어 같은 페이지에 재게시한다. 요구 자체는 이 단계에서 바뀌지 않는다.
  • 승인 해시는 분해안을 포함한다. Jira 티켓은 승인 뒤 쓰기 단계가 만든다.
  • 승인 뒤 요구 변경으로 생기는 추가 티켓(§6.2)은 다시 승인받지 않고 종료 보고서에 적는다. 가정

§6승인 이후 규칙

§6.1새 모호성

  • 물을 수 있는 것은 계획 단계(게이트)에서 미리 묻는다. 결정 영향 분석에서 드러난 막힐 것(없는 에셋, 없는 API 필드 등)을 게이트 질문으로 올리는 것이 그 수단이다.

    2. 경험 점검: 시나리오의 각 화면과 전환을 사람 관점의 점검표로 본다. 점검표는 과거 QA 결함에서 뽑는다(예: 잘림, 겹침, 눌리지 않음, 빈 화면, 오류 문구 없음, 뒤로 가기 이상, 키보드 가림). 근거는 스크린샷이나 녹화다.
  • 처리 결정
    • 명백한 결함(깨짐, 잘림, 겹침, 먹통, 크래시)은 빌더가 고치고 다시 검증한다. 통과할 때까지 반복하되 상한과 환경 실패/결함 분류를 둔다.
    • 시안·요구대로지만 불편해 보이는 것("경험 우려")은 고치지 않고 QA 보고서와 PR 본문에 근거 화면과 함께 남긴다.
  • 시나리오 결정
    • 설계는 승인 전, 실행은 구현 후.
    • 기대 결과는 잠근다. QA 가 고칠 수 있는 것은 절차(셀렉터, 대기)뿐이다.
    • 에이전트 탐색은 처음 한 번만 하고, 통과한 경로는 결정적 스크립트로 고정해 재실행한다.
  • 모킹 결정: OpenAPI 에서 만든 mock 을 쓰고 시나리오마다 실서버/모킹을 표기한다. 모킹으로만 통과한 시나리오는 보고서에 "통합 미검증"으로 남긴다.
  • 기기 결정: 처음부터 iOS 시뮬레이터와 Android 에뮬레이터 둘 다 통과해야 PR 을 올린다.
  • 테스트 계정 결정: 사용자가 준 테스트 계정으로 워크플로우가 직접 로그인한다. 계정이 여러 개 필요하면(역할·구매 이력이 다른 상태 등) QA 설계 단계가 필요한 상태를 적어 게이트에서 요청한다. 계정 정보는 저장소 밖 파일에 두고 문서·heka·로그에 비밀번호를 남기지 않는다. 가정2026-10-20 결정 8 계승
  • 서버 결정: 일감마다 쓰는 서버가 다르므로 워크플로우가 직접 고른다. 변경된 API 가 반영돼 있는 환경을 찾는 것이 기준이다. 방법 가정: 영향 분석에서 뽑은 변경 API 경로·필드를 환경별 openapi.json(staging, dev-N)과 대조해 모두 있는 환경을 고르고, 고른 환경과 근거를 게이트 문서와 QA 보고서에 적는다. 어느 환경에도 없으면 해당 시나리오는 모킹으로 표기한다.
  • 산출물: 시나리오별 스크린샷, 사람에게 가는 QA 보고서, PR 에 붙는 AS-IS·TO-BE.
  • PR 스크린샷 결정과거 PR 을 따른다
    • 형식 사실: 본문의 ## 스크린샷 절에 화면 묶음별 소제목을 두고, 상태 이름을 머리글로 한 HTML 표에 <img src="…" width=300 /> 로 넣는다(PR #1749 등, heka pr-300px-img-width-300).
    • 올리는 방법 사실: gh pr create|edit --attach 로 올린다(gh 2.99.0 이상, 이 머신은 2.103.3). 치환은 마크다운 이미지 참조에만 되므로 ① 마크다운 참조로 올려 asset URL 을 받고 ② 본문을 HTML 표로 다시 써서 저장하는 두 단계다(heka github-image-upload-no-documented-api-gh-attach-2026-10). 올린 asset 은 지울 수 없다.
  • 도구 후보 사실: Maestro 2.12.1 은 MCP 를 내장한다(화면 계층 조회, 스크린샷, YAML 실행). agent-device 는 탐색 세션을 기록해 호환 흐름을 Maestro YAML 로 내보낸다. Maestro 의 AI 단언은 실험 기능이고 화면이 Maestro Cloud 로 나가므로 게이트로 쓰지 않는다. Maestro 에는 네트워크 모킹이 없다.
  • 알려진 어려움 사실: 대상 앱에 testID 와 E2E 자산이 거의 없다. 과거 Maestro 시도는 딥링크 이동을 한 번도 확인하지 못했다. 모달·바텀시트·에러·빈 상태는 딥링크로 도달하지 못한다. 에이전트의 QA 판단은 보정 없이는 관대하다.

§10평가와 점진적 개선

"같은 일감은 반복할 수 없다"는 제약은 평가 장치로 푼다. 결정동의

  • 리플레이: 과거 일감을 당시 base SHA, PRD 버전, 지식 시점으로 복원해 여러 번 다시 돌린다.
  • 결함 주입
    • 매니저 사수: 요구 하나를 지우거나 바꾼 문서를 주고 잡는지 본다.
    • 코드 리뷰어: 인수 조건 위반을 심고 잡는지, 정상 코드를 결함으로 오판하지 않는지 본다.
    • QA: 앱에 알려진 버그를 심고 시나리오가 잡는지 본다.
  • 병행 실행: 사람이 실제 업무를 하는 동안 외부 쓰기 없이 같이 돌려 비교한다.
  • 외부 쓰기 0 결정: 리플레이·결함 주입·병행 실행에서는 Confluence·Jira·GitHub 에 실제 결과물을 올리지 않는다(이미 있는 결과물과 중복되기 때문이다). 티켓은 파일로, PR 은 로컬 브랜치와 본문 파일로만 남긴다. 평가 모드에서는 쓰기 단계 자체를 띄우지 않아 구조로 막는다. 가정
  • 컨텍스트 차단 결정: 이미 작업된 PRD 를 다시 돌릴 때는 그 일감의 기존 작업을 모르는 상태로 진행한다(편향 방지). 차단 대상 가정
    • 코드: 저장소를 당시 base SHA 로 복원하고 이력을 단일 커밋으로 다시 만든다. base 는 PR 의 base.sha 가 아니라 first-parent 이력에서 직접 계산한다(heka github-pr-base-sha-not-creation-time-r2).
    • 문서: PRD 는 당시 버전을 읽는다(heka confluence-version-history-via-atlassian-mcp-prd-d9-r3). 그 일감의 [MO] 하위 작업, PR, QA 티켓은 읽지 못하게 한다.
    • 지식: heka 는 당시 시점(known_at)까지만 보이게 하고, 그 일감에서 나온 노트(게이트 결정, 대조 기록)는 뺀다. 세션에 자동으로 붙는 heka 주입 훅도 같은 시점으로 고정하거나 끈다. 미결방법 실측
    • 기록: 과거 세션 원문(recall)과 메모리는 읽지 못하게 한다. 실행 에이전트는 모두 새 세션으로 띄운다.
    • 채점표(gold)는 에이전트가 볼 수 없는 곳에 두고, 사람이 에이전트 산출물을 보기 전에 교정한다(heka hew-slice1-decisions-2026-10-20).
    • 한계 미결: Figma 는 과거 버전을 읽는 수단을 확인하지 못했다. 현재 시안을 읽으면 그 뒤의 수정이 섞인다.
  • 프롬프트를 고치며 들여다본 케이스와 채점에만 쓰는 케이스를 나눈다. 제안 APP-3008·APP-2513 은 실패 내용이 이미 설계와 heka 규칙에 반영돼 있어, 이 둘의 점수만으로는 새 일감에서도 통하는지 알 수 없다.
  • 회귀 케이스는 실제 실패에서 뽑는다. 이미 가진 실패(시안 instance 교체 누락, 추정으로 닫은 범위, 운영자 행 인용)가 첫 케이스다.
  • 비결정적이므로 케이스마다 여러 번 돌리고, LLM 채점기는 사람 판정과 맞춘다.
  • 좁은 행동 회귀는 claude plugin eval 로(케이스당 기본 3회, 플러그인 없는 기준선 비교, MCP mock). 요구 재현율처럼 계산이 필요한 채점은 자체 러너로.
  • 평가로 정할 실험
    1. 사수의 모델 등급(Haiku 5.5 로 충분한가, 시안 시각 대조 포함).
    2. 빌더 effort: medium 대 low.
    3. 빌더 단일 대 분석·코드 분리(큰 반복 작업에 한해).
    4. 설계 단계(테크니컬 매니저, QA 설계): Opus 5.5 high 대 Fable 5.2 medium(§4.5).
  • 실수 기록 형식(처음부터 남긴다): 발견 단계, 원인 단계, 유형, 근거, 당시 프롬프트·에이전트 정의 버전(git SHA), 실행 id.
  • 프롬프트를 고치는 규칙 가정
    • 규칙을 하나 넣을 때 그 규칙을 낳은 실패를 회귀 케이스로 같이 넣는다.
    • 고치는 순서는 코드 검사 > 스키마·패킷 > 절차 > 프롬프트 문장이다.
    • 주기적으로 규칙을 빼 보고 점수가 안 떨어지면 지운다.

§12구축 순서

  • 순서 결정: 요구 분석과 게이트부터 깊게 만든다.
  • 1번 단계의 범위: 테크니컬 매니저(영향 분석 포함), QA 전문가(설계), 매니저 사수, 게이트 문서, 승인. 분해안이 게이트에 실리게 됐으므로 티켓 메이커와 티켓 사수도 이 범위에 넣는다. 가정 Jira 쓰기 단계는 넣지 않는다.
  • 결정 1번 단계의 완료 기준을 미리 정한다. 과거 PRD 2~3건을 다시 돌려 요구 재현율, 사후에 틀린 확정 항목 수, 게이트 체류 시간이 기준을 넘으면 다음 단계로 넘어간다. 옛 hew 는 같은 경로에서 뒤 단계를 한 번도 돌려 보지 못했다. 이 리플레이는 §10 의 외부 쓰기 0 과 컨텍스트 차단을 지킨다. 기준 수치는 미결(§13 의 8)이다.
  • 결정 QA 는 작은 확인만 먼저 한다. 두 플랫폼에서 화면 하나에 도달해 캡처하는 것까지다. 가장 불확실한 단계가 가장 넓은 범위로 맨 뒤에 놓여 있기 때문이다.
  • 이후 순서 제안: 진행 프로그램과 빌더·사수·리뷰 → QA 실행 → PR 작성.

§16적용하는 heka 규칙

역할별 규칙 id 는 프로필의 heka 에 둔다(§17). 결정 각 단계의 패킷에는 그 단계의 규칙 id 만 싣고, 에이전트는 본문을 heka_expand 로 읽는다. 사람이 말한 것이 아니라 AI 가 뽑아 검수되지 않은 노트는 적용 전에 본문을 확인한다.

§17프로필: 도메인·팀에 특화된 값은 저장소 밖에 둔다

결정 특정 서비스·팀에 묶인 값(주체 낱말, 티켓 제목 형식, SP 범위, PR 상한, 역할별 heka id, 외부 서비스 주소, 도메인 설명)은 저장소가 아니라 프로필 폴더에 둔다. 저장소는 가상의 서비스로 채운 예시(profiles/example)만 가진다.

  • 위치를 정하는 순서: 환경 변수 HEW_PROFILE_DIR → ~/.hew/profile(폴더가 있을 때) → 저장소의 profiles/example(끝 기본값).
  • 파일 두 개: profile.yaml(필수), domain.md(선택. 없거나 비면 해당 패킷 절을 뺀다).
  • profile.yaml 키: actors(주체별 판정 낱말, 정규식 조각, 대소문자 무시), plan(sp, title.format, pr.max_tickets·pr.base, 선택 notes), heka(역할별 규칙 노트 id), connections.atlassian_cloud_id. 알 수 없는 키와 틀린 값은 어느 파일의 어느 키인지 알리고 내부 오류로 멈춘다.
  • 패킷: domain.md 는 ## 도메인 안내 절로 그대로 실린다(## 따를 규칙 앞). 역할 정의가 이 절을 가리키는 테크니컬 매니저와 QA 설계의 패킷에만 싣는다. 사수 패킷에 실으면 결함 주입 평가에서 포착이 떨어졌다(같은 결함 하나를 반복해 쟀을 때 실으면 4번 중 0번, 싣지 않으면 10번 중 7번. 표본이 작아 다시 잴 필요가 있다). ticket-maker·ticket-sasu 패킷에는 ## 팀 규칙 절(제목 형식, SP 범위, PR 상한, base, notes)이 실린다.
  • 저장소의 rules/ 에 남는 것: 역할의 모델·도구·참고 파일(roles.yaml), 수집 한도와 허용 도구(collect.yaml), 티켓 본문 금지 규칙(plan.yaml 의 body_forbidden).
  • 가드 훅의 "수집 프로필"(HEW_GUARD_PROFILE)은 이것과 다른 것이다. 훅이 어떤 도구를 허용할지 정하는 모드일 뿐 프로필 폴더와 무관하다.
  • 테스트는 환경 변수로 profiles/example 을 고정해 개발자 홈의 실제 프로필이 섞이지 않게 한다.
